## 第一章 零售生态地形图

> 🧭 **导读**：一人红队的交战像给一家单体公司做年报审计——资产就摆在授权书里；企业生态渗透像给集团做**合并报表**——先把并表范围理清，再谈科目明细。本章给你零售产品生态的四层解剖图、"一个 App 牵出二十个内部服务"的测绘五步法、零售数据三级分类与各自红线。方位：你现在站在生态上空，先看地形再落地；第二章会把你按链路扔进战场。

### 1.1 产品生态解剖：四层地形

| 层 | 典型功能域（行业通用称谓，非任何企业系统名） | 攻击面特征 | 渗透视角 |
|---|---|---|---|
| 前台层 | 购物 App、小程序、Web 商城、POS 收银、自助收银、电子价签、客服工作台 | 多端并存、版本碎片化、旧接口长期共存 | 入口与流量层：抓包起点，旧版本逻辑的藏身处 |
| 中台层 | 订单中心、库存中心、价格中心、促销中心、支付中心、会员中心、搜索推荐 | 服务间调用密集、常内网互信、算价与状态机集中 | 业务逻辑漏洞主战场（第二章五链大多落在这层） |
| 后台层 | 供应链采购、供应商协同门户、财务结算与对账、经营报表 | 内控流程线上化、外部租户（供应商）接入 | 越权与内控绕过（供应链链）；横向后的高价值区 |
| 边缘层 | 第三方物流对接、支付渠道、营销短信、开放平台 API、门店 IoT | 边界模糊："哪段是我们的系统"最易扯皮 | 回调伪造、密钥管理、越界测试的高风险区 |

```
        ┌──────────────── 前台层 ────────────────┐
        │  App    小程序    Web    POS    自助收银  │
        └───────────────────┬────────────────────┘
                            │ 统一接入（API 网关 / CDN / WAF）
        ┌───────────────────▼────────────────────┐
        │ 中台层：订单·库存·价格·促销·支付·会员·搜索  │
        └────────┬──────────────────────┬────────┘
                 │                      │
     ┌───────────▼───────────┐   ┌──────▼───────────────────┐
     │ 后台层：供应链·供应商门户 │   │ 边缘层：支付渠道·物流·短信   │
     │        财务结算·报表     │   │        开放平台·门店 IoT    │
     └───────────────────────┘   └──────────────────────────┘
```

四条地形要点（每条都对应后文一整章的攻击面）：

1. **多端一致性是前台层最大攻击面**：App 最新版、两年前的小程序旧版、POS 固化版本，常共用同一批网关路由；旧端未随新端收紧校验，形成"多端权限模型断层"（第四章 4.2 ⑤）。
2. **中台服务间常是内网互信**：服务间调用不鉴权或仅静态 token，一旦从前台漏洞摸到服务调用面，横向成本极低——VOL-03 的内网方法论在这里无缝接上。
3. **后台层是内控审计的线上化**：审批流、对账、结算全部变成接口，越权测试相当于给内控做穿行测试（R-SC-02/R-SC-03）。
4. **边缘层先问归属**：第三方域名、渠道回调地址不属于本企业资产，测试前先过授权确认（1.2 陷阱①）。

### 1.2 生态型目标测绘法：一个 App 牵出二十个内部服务

> 📊 **审计类比：生态测绘＝合并报表并表范围梳理**。审计师判定并表范围看"控制权"，你判定渗透范围看**数据流与调用链**——凡是接触本企业数据（订单/会员/卡/策略价）的系统都在生态内，无论部署在哪个云、哪个团队名下。漏并一家子公司，报表整体失真；漏测一个服务，覆盖台账出现负空间（VOL-09C ⑨）。并表范围从股权结构图出发，渗透范围从数据流图出发。

五步法总表：

| 步骤 | 动作 | 主要工具/依据 | 产物 |
|---|---|---|---|
| ① 抓包域名清单 | App/小程序/Web/POS 四端全业务流程抓包 | 代理 + VOL-05 客户端分析、VOL-01 侦察 | 四端域名清单（按端标注） |
| ② CDN 剥离 | CNAME 链解析，识别 CDN/WAF 接入层 | DNS 解析、响应头、证书特征 | 接入层/源站分层表 |
| ③ API 网关路由 | 归并统一前缀，按路径首段聚类 | 路径规律、统一错误结构 | 路由→服务映射表雏形 |
| ④ 内部服务命名规律 | 从路径/报文/错误页提取服务名并按规律推测 | 命名后缀规律（-center/-service/-svc） | 内部服务清单（待确认） |
| ⑤ 影子资产 | 环境前缀、旧版接口、遗留域名、JS 常量 | 证书透明度日志（公开）、历史 DNS | 影子资产清单（授权灰区） |

**① 抓包域名清单**。四端各走一遍核心业务：浏览→搜索→加购→下单→支付→退款→会员中心→客服工单，代理落地为去重域名清单并标注来源端。小程序可用开发者工具代理；App 的证书校验（SSL Pinning）处理见 VOL-05；POS 在门店内网，需要门店测试环境与**专项授权**，不塞进常规交战单。产物按端分组——同一个功能域在四端的域名差异本身就是信息（App 直连中台、Web 走统一网关）。

**② CDN 剥离**。对每个域名做 CNAME 链解析，用响应头（X-Cache、Via、Server）、证书 CN、解析 TTL 特征识别 CDN/WAF 接入。目的**不是**"穿透 CDN 打源站"（那需要单独立项授权），而是分清请求落在接入层还是源站：把 WAF 的拦截响应误当业务校验，是新手第一大误判（陷阱②）。

**③ API 网关路由**。统一路径前缀（`/api`、`/gateway`、`/h5`、`/pos`）、统一 401/403 错误结构、token 格式全站一致，都是网关特征。按路径首段聚类（`/oc/*`、`/mc/*`、`/pc/*`），得到"路由 → 后端服务"映射表。

**④ 内部服务命名规律**。从路径、响应体的 `service` 字段、错误页、埋点上报样例里提取服务名：`/oc/v2/createOrder` + 响应 `"service":"ORDER-CENTER"` → 存在订单中心。同一生态命名高度规律（-center/-service/-svc 后缀、两到三字母缩写前缀），可按规律扩展推测会员中心、库存中心。**推测出的服务名进"待确认清单"，不是可打资产**（陷阱③）。

**⑤ 影子资产**。test/uat/pre/grey 环境前缀域名、历史大促活动页遗留域名、`/v1` 旧版接口、前端 JS 常量里的内部域名；证书透明度日志（crt.sh 类公开服务）查历史子域。影子资产是内部渗透的高价值区（环境校验弱、数据有时反而真），也是授权灰区——先走归属确认流程（第五章 5.2）再动手。

产物契约（与第六章 redteam-agent 目录衔接）：

| 产物 | 内容 | 关键字段 |
|---|---|---|
| `inventory/systems.yaml` | 生态资产清单 | domain / 端 / 层级 / 负责团队 / scope 状态（在授权·待确认·外部）/ 数据级别 |
| `inventory/routes.md` | 路由→服务映射 | 前缀 / 服务名 / 鉴权形态 / 来源端 |
| `inventory/shadow.md` | 影子资产 | 域名 / 发现方式 / 归属确认状态 |

清单样例（虚构片段，字段契约见第六章 6.1）：

```yaml
# inventory/systems.yaml（示意，全部虚构）
- system: ORDER-CENTER
  domain: oc.nanhua.example
  layer: middle                    # front / middle / back / edge
  owner: 订单团队
  scope_status: authorized
  data_class: [personal, order]    # 接第三章数据分级
- system: PAY-CENTER
  domain: pay.nanhua.example
  layer: middle
  owner: 支付团队
  scope_status: authorized
  data_class: [card-data]          # 最高级：碰卡红线适用（第三章 3.1）
- system: vendor-portal
  domain: supplier.nanhua.example
  layer: back
  owner: 供应链团队
  scope_status: pending            # 待授权：影子资产走归属确认（第五章 5.2）
  data_class: [personal, strategy]
```

**【陷阱】** ①第三方域名混入：统计 SDK、短信厂商、地图服务域名会大量出现在抓包里，逐一标"外部"，测它=越界；②CDN 拦截误判：WAF 的 403 与业务校验的 403 报文形态不同（HTML 拦截页 vs JSON 业务码），先分层再定性；③推测≠授权：按命名规律"猜"出的服务直接发请求，等于对未授权资产发起测试；④POS 与门店内网需要物理位置或专线，属于专项授权形态。

**【AI 位】** 把去重后的域名+路径清单结构化（JSON 表）喂给 AI，产出"服务归属猜测表"（域名/路径 → 猜测服务 → 置信度 → 依据），你人工裁决后入清单。喂养与验收纪律见 VOL-09C §1.1/§1.3：猜测表必须带"依据"列，无依据的猜测直接删；AI 只做聚类与规律归纳，scope 判定永远是人签字。

### 1.3 零售数据分类分级与测试红线

| 数据类别 | 典型字段 | 生态内高频出现位置 | 分级 | 测试红线（一句话） |
|---|---|---|---|---|
| 支付卡数据 | PAN、CVV、磁道/芯片等效数据、有效期 | POS 内存与日志、支付中心、客服系统、回调日志、小票 | 最高 | 能看不能存；CVV 绝不构造测试；磁道只证存在不提取（第三章 3.1） |
| 敏感个人信息 | 身份证、收款银行卡、人脸/指纹、精准收货地址+行踪 | 会员中心、订单、退款收款账户、刷脸支付链路 | 高（PIPL 敏感个人金融信息） | 他人数据只证"可达"，响应体不落盘、截图重度脱敏（第三章 3.2） |
| 一般个人信息 | 手机号、昵称、订单记录、浏览行为 | 全生态流转 | 中 | 用自产测试账号数据；证据脱敏按 VOL-07-08 B4 |
| 商业策略数据 | 成本价、促销规则与预算、供应商合同价 | 价格中心、促销中心、供应链、财务 | 高（商业秘密） | 不出生态：不外传、不进外部 AI prompt（第五章 5.8） |
| 经营数据 | 销量、库存水位、报表 | BI、库存中心 | 中高 | 报告只引用聚合数字，不贴明细表 |

三句口诀（先背口诀再干活）：**卡数据「能看不存」、客户数据「自产自用」、策略数据「不出生态」**。每句在第三章都有对应的操作细则与违规处置流。

## 第二章 业务逻辑漏洞场景库（核心章）

> 🧭 **导读**：VOL-02 教过你订单状态机、竞态这些"单点漏洞"；本章把它们放进零售的五条业务链——交易、促销、退款、会员、供应链。形态从"教程"变成"场景库"：每个场景固定六段（【原理】【测试方法】【验证】【修复】【陷阱】【AI 位】），可枚举、可查阅、可转化为自动化检查（第六章）。审计类比：这是你的**会计科目余额表**——交战时逐科目过账，每个场景是一个科目，测试就是过账，覆盖台账就是试算平衡表；科目齐全不等于账平，但没有科目表一定会漏账。

**编号规则**：`R-TX-xx` 交易链 / `R-PX-xx` 促销链 / `R-RF-xx` 退款链 / `R-MB-xx` 会员链 / `R-SC-xx` 供应链链。示例报文一律以虚构的南华优选 `api.nanhua.example` 为形，接口与响应均为教学构造。

**六段结构说明**（每场景固定六段，工单与报告按段名引用）：

| 段 | 回答什么 | 在工单里的用法 |
|---|---|---|
| 【原理】 | 业务规则哪里错（根因归类） | triage 定性依据 |
| 【测试方法】 | 构造什么请求（入口动作） | 复现步骤的骨架 |
| 【验证】 | 成立/不成立的判据（对账口径） | 复测通过标准 |
| 【修复】 | 修复方向（一句话工程解） | 修复建议段 |
| 【陷阱】 | 测试 vs 生产 / 风控对抗的坑 | 环境与护栏说明 |
| 【AI 位】 | AI 能帮哪一步、边界在哪 | 协作方式说明 |

五链关系图（先建立链路观，再看场景）：

```
交易链 ──── 下单 → 支付 → 履约 → 状态机（资金主链）
促销链 ──── 券 / 满减 / 秒杀 / 积分（挂在交易链每个节点上的"加权器"）
退款链 ──── 仅退款 / 退货退款 / 部分退款（交易链的逆向链，促销要逆向冲销）
会员链 ──── 等级 / 权益 / 积分账户（横跨所有链的身份与资产负债底座）
供应链链 ── 采购 → 入库 → 对账 → 结算（后台资金另一端，B2B 面）
```

为什么零售生态的业务逻辑漏洞比通用 Web 多：**规则复杂度**（促销叠加×退款冲销×多端差异的组合爆炸）与**组织复杂度**（每个中心一个团队，规则在团队边界上失配）相乘。你 5 年源码审计的"业务规则读解"能力在这里是核心竞争力——黑盒选手看到的是报文，你看到的是分录。

### 2.1 交易链

#### R-TX-01 价格篡改（客户端回传金额）

**【原理】** 算价责任错位：服务端信任了客户端回传的金额字段。正常链路是"前端展示价 → 用户提交 SKU+数量 → 服务端价格中心算价"；漏洞形态是下单请求携带 `unitPrice/totalAmount/payAmount` 且服务端直接采用，或总额虽重算、**子项**（运费、优惠券抵扣、包装费、凑单品改价）未参与服务端重算。审计视角：把"金额字段来源"当污点分析做。

**【测试方法】** Burp 拦截下单接口（形如 `POST /oc/v2/order/create`），构造三组对照：①`totalAmount` 改 0.01；②只改运费 `freightFee=-999` 或 0；③只改券抵扣 `discountAmount` 抬高。每组一次只改一个字段——对照实验纪律同 VOL-02 1.1 的 IDOR 测试。

**【验证】** 订单创建成功且**订单详情与收银台、支付中心流水三方一致地等于篡改值**（以支付流水为准，不是前端显示）。判据分级：篡改后创建成功=实锤；创建失败但报错差异可佐证"部分字段重算、部分不重算"。证据三联：请求、响应、订单详情页（金额来源可信方）。

**【修复】** 服务端全量重算：金额字段一律服务端生成，客户端回传金额仅作展示对账；下单与支付两侧以服务端价格快照为准，子项（运费/抵扣/附加费）同样入快照。

**【陷阱】** ①多数中台已重算总额，但子项常漏——篡改面要枚举全部金额类字段，别只打 totalAmount；②生产环境验到"订单创建成功"即停，绝不真实支付（第三章 3.3）；③同 SKU 反复下单会触发风控刷单模型，测试账号+报备（第五章 5.2），别把风控限权误判为"已修复"。

**【AI 位】** 把下单/支付/退款三个接口的完整报文喂给 AI，产出"金额类字段清单+每字段责任方猜测表"（客户端生成/服务端生成/混合），逐字段设计对照实验——喂养格式见 VOL-09C §1.1，表必须带"依据"列，你逐行裁决。

#### R-TX-02 数量负数与小数

**【原理】** 数量校验缺失：`quantity` 未约束为正整数。负数数量使总额为负（叠加支付环节成为倒扣）、库存反向增加；小数数量对生鲜称重品（按克）合法，但标品 SKU 复用同一接口时未按 SKU 属性收紧。审计视角：校验常写在 Controller 而不在公共入口层，于是"换一个入口就漏"。

**【测试方法】** ①`quantity=-1`（观察总额与库存变化方向）；②`quantity=0.5 / 0.001`（标品）；③主链通过后逐个重测旁路入口：立即购买直传参、购物车改数量、合并支付、凑单改量——同一校验常只在主下单链做了。

**【验证】** 负数：订单总额为负或 0、库存不减反增（以库存中心接口为准）；小数：标品订单创建成功且按小数计价/计库存。两个方向任一成立即实锤。

**【修复】** 入口统一校验：数量为正整数（称重类按 SKU 属性放宽为正数+精度上限），校验收敛到服务端公共层（参数绑定/网关插件），不是每个接口各写一份。

**【陷阱】** ①"购物车改数量"接口常被修，"立即购买直传参"和"合并支付"入口漏——接口清单去重后全量过一遍；②生产测负数会真实回补/扣减库存：先在 UAT 验存在性，生产只做无害重放（不落库的校验路径）；③总额为负但要实际"支付"才构成资损，验到创建即可，别走支付。

**【AI 位】** 让 AI 按接口清单生成边界值矩阵（-1 / 0 / 0.5 / 1 / 1e9 / 超长小数位 × 全部数量入口），输出为可执行用例表；你补上"每个入口的业务语义"列（哪个是称重豁免入口）。

#### R-TX-03 并发超卖

**【原理】** 库存扣减的非原子性：check-then-act（先查库存再扣减）之间无锁。并发 N 个请求同时读到 stock=1，各自判定可买，全部下单成功。变体：库存预占后支付超时不释放（少卖）；乐观锁版本号未参与 UPDATE 条件（形同虚设）；"校验库存"与"下单"分离成两个接口，两段之间无占位。

**【测试方法】** 低峰期对单一 SKU（库存=1）并发提交约 20 个下单请求（Python asyncio/aiohttp 模板见【AI 位】，或 Burp Intruder 并发模式）；若校验与下单分离，对两段分别并发。脚本先在 UAT 演练，并发数、目标 SKU 写进交战日志。

**【验证】** 成功订单数 > 库存可售数，且库存中心该 SKU 透支为负；或订单成功但库存扣减数 < 成功订单数（超卖/少卖双形态都要记）。对账口径：成功单数、库存变化、支付流水三方。

**【修复】** 原子扣减：`UPDATE stock SET n=n-1 WHERE sku=? AND n>=?` 以影响行数判定，或 Redis Lua/分布式锁串行化；预占-释放配对事务化，超时自动回补。

**【陷阱】** ①生产并发测试本身是资损风险：限额（≤20 并发）、低峰窗、选可回滚的测试商品、报备四护栏缺一不可（第三章 3.3）；②高并发会触发网关限流/WAF，把"被限流"误判为"无漏洞"——响应要区分 429/503 与业务拒绝；③重放要换新会话与幂等键，否则测的是幂等而不是并发（两个不同缺陷）。

**【AI 位】** 让 AI 写并发脚本模板（asyncio+信号量，参数化 URL/并发数/幂等键/账号池）与"成功单数-库存变化"对账输出；**并发数护栏由你人工设定并写死在脚本头**——AI 不决定测试强度（VOL-09C §4.4 契约）。

#### R-TX-04 订单状态机绕过

**【原理】** 状态机非法迁移未被拒绝：待支付→已发货、已签收之外的退款入口等"跳态"被接受。根因：状态变更接口只校验登录态，不校验当前状态与迁移合法性；或前端状态机与服务端枚举不一致（旧端少一个中间态）。最高危变体：**支付回调伪造**——回调报文无验签或弱验签，攻击者直接把订单推成"已支付"。VOL-02 2.1 讲过单点，这里是生态形态：状态机分布在订单/支付/履约三个中心。

**【测试方法】** ①先抓正常全流程拿到状态枚举集，再对 cancel/confirm/ship/deliver 等接口传"跳态"组合（待支付单直接传 ship、已发货单传 cancel）；②支付回调伪造只在**渠道沙箱**做：拿沙箱回调报文改 orderId 重放（生产回调地址绝不可碰，第三章 3.1）。

**【验证】** 非法跃迁被接受（订单状态变更成功，且后续履约/退款逻辑按新状态走）；回调伪造则订单变已支付而支付渠道无对应流水——资金侧对账不一致即实锤。证据同样三方：订单状态接口、状态变更响应、渠道/资金流水。

**【修复】** 服务端状态机表驱动：合法迁移白名单（from, to, operator, 条件），迁移加乐观锁防并发跳态；支付回调验签 + 渠道流水核对 + 金额核对三重校验。

**【陷阱】** ①生产订单状态被污染要运营工单恢复——测前确认恢复手段存在再动；②先验"拒绝路径"（预期 4xx）再验"接受路径"，留下正反对照证据，防"本来就是非法参数"的质疑；③POS 端与 App 端的状态枚举可能不同步，多端各抓一份枚举再对比（接第四章多端断层）。

**【AI 位】** 把全量抓包中含 `status/orderState` 字段的请求喂给 AI，产出"状态枚举集+迁移边猜测图"（每条边标注观测来源），你在图上圈出非法边逐一验证——图本身就是报告素材。

### 2.2 促销链

#### R-PX-01 优惠券生成·叠加·复用·转赠

**【原理】** 券生命周期四处断点：①**生成**——券码可预测（顺序号/时间戳弱随机）或领券接口可重放；②**叠加**——互斥规则只在前端判断，或后端只校验单张合法性不校验组合；③**复用**——核销与订单非事务，同一张券并发核销或退款后未冲销可二次使用；④**转赠**——转赠只换绑定不改券状态，赠出后双方均可核销（双花）。

**【测试方法】** ①领券接口重放（同 token 同 activityId 三次）；②同订单叠两张同类型券、券+满减+会员折扣全组合提交；③核销并发：一张券挂两个订单同时支付；④转赠后 A、B 账号先后使用同一券码。

**【验证】** 任一断点成立即实锤：重放多领（券账户余量变化）、互斥组合通过（订单优惠明细）、一券多用（券流水两条核销）、转赠双花（双方核销记录）。以促销中心券流水为最终口径。

**【修复】** 领券幂等（会员×活动唯一约束）；叠加互斥规则收敛到服务端规则引擎统一裁决；核销原子（券状态机+唯一索引）；转赠原子换绑（旧绑定即时失效，换绑与通知同事务）。

**【陷阱】** ①券是真实营销预算：生产测试造成的多领要立即上报业务清退，测完自查券账户余额差异（第五章 5.6 上报流）；②风控"羊毛模型"会盯测试账号的重复领券，账号被限权后误判"接口修了"——区分风控拦截与业务校验拦截（响应码与文案不同）；③转赠与冒领测试只用自己注册的测试账号，不碰他人券（PIPL 红线，第三章 3.2）。

**【AI 位】** AI 归纳券模板字段（类型/面额/互斥组/有效期/适用范围）与领券-核销-转赠接口参数对照表，标出"仅前端生效字段"疑点清单——疑点清单只是测试候选，逐条人工验证。

#### R-PX-02 满减计算顺序与优惠分摊

**【原理】** 促销叠加的顺序敏感：先打折再满减与先满减再打折结果不同；下单端与退款端是**两套实现**（下单按顺序 A 算，退款按分摊比例 B 退），差额可被套利。优惠分摊：总优惠按比例摊到各 SKU，退款单件时若按"原价-错误分摊"退，多退部分即资损。审计视角：这是"两个部门各自实现的同一会计政策"，差异=未调节分录。

**【测试方法】** 构造组合单（满 300 减 50 + 8 折 + 10 元券）：①对比收银台金额、订单详情金额、支付流水三方一致性；②退其中一件，核对退款额与按分摊快照应退额；③若请求存在 `promotionOrder/promotionPriority` 类字段，改顺序重算对比；④极端值：单件刚好踩满减线、退后剩余金额跌破线的边界单。

**【验证】** 三方金额不一致、或"退款总额 + 剩余商品实付 ≠ 原实付"（分摊守恒破坏）即实锤。守恒校验式：`Σ(各件实付-各件退款) == 订单实付`。

**【修复】** 促销计算收敛为单一规则引擎服务，顺序显式配置且下单/退款/展示全链一致；优惠分摊在下单时固化为快照，退款一律按快照退、冲销按快照反向。

**【陷阱】** ①分/元单位混用造成的 ±0.01 级差异是精度 bug 不是套利，定级克制（低危+工程修复），别拿 1 分钱差异当资损上报；②组合促销的"合法顺序"以业务规则文档为准——先找促销产品 Owner 确认规则再定性，否则会被"这是 feature"顶回（第五章 5.5 话术表）。

**【AI 位】** AI 做三方报文（收银台/订单详情/退款响应）的字段级 diff，输出差异字段表——这是把源码审计的"两处实现比对"迁移到黑盒报文的典型打法。

#### R-PX-03 秒杀资格与库存

**【原理】** 资格与下单非原子：资格 token 可复用（查资格与消耗资格分离）；秒杀库存与普通库存混用（秒杀加购后走普通结算路径，按普通库存成交）；前端倒计时与后端开闸时间不一致（提前下单）；资格校验只在前端埋点层（点秒杀按钮才查，直连接口不查）。

**【测试方法】** ①持资格 token 连续下单 N 次（N=限购+2）；②秒杀 SKU 加购后走普通结算路径；③未到开闸时间直接请求下单接口（绕过倒计时）；④无资格 token 直接调下单接口（资格字段置空/置 0）。

**【验证】** 超出限购的成功订单、秒杀价+普通库存成交、开闸前订单创建成功、无资格下单成功——四判据任一成立。以秒杀活动后台的成交名单为最终口径。

**【修复】** 资格消耗原子化（token 一次性、会员×活动唯一约束）；秒杀库存独立库存池；开闸时间服务端裁决+接口令牌桶；资格校验放下单接口服务端。

**【陷阱】** ①生产秒杀活动测试=直接资损事故：一律在活动测试场（压测环境带秒杀开关）验证机制，生产只在**非活动的测试 SKU** 上验存在性；②秒杀流量是风控重灾区，测试并发会触发熔断，误判"无洞"——看熔断响应与业务拒绝的差异；③秒杀页的签名参数（sign/timestamp）过期快，重放要先生成新签名，别把签名过期当资格校验。

**【AI 位】** AI 从秒杀页 JS 与抓包中提取资格相关字段（token/sign/timestamp/activityId）语义表，标注"可复用候选"与"一次性候选"，并生成字段重放组合清单。

#### R-PX-04 积分汇率与转移

**【原理】** 积分账目三处错位：①**汇率可控**——`exchangeRate/pointDeduct` 随请求提交，服务端不校验；②**转移无限额非原子**——A→B 转赠并发双花（同积分同时转给两个接收方）；③**精度截断套利**——积分抵现在一侧四舍五入、另一侧向下截断，多笔小额各抵一次累积差额。

**【测试方法】** ①改 `payPoints` 超持有量、改汇率放大抵扣面额；②两个测试账号对同一笔积分并发转赠（双接收方）；③构造多件小额订单逐件用积分抵扣，对比积分扣减总额与抵扣金额总额的换算差。

**【验证】** 积分账户凭空增加（转出方未减而接收方已加）、或累计抵扣价值 > 积分应有价值。以会员中心积分流水对账（期初+收入-支出=期末，逐账户核）。

**【修复】** 汇率服务端配置只读下发；转出原子（余额检查与扣减同事务+唯一流水号防重）；抵扣计算与记账同精度同舍入策略。

**【陷阱】** 积分是**负债科目**：凭空增分影响财务口径与营销预算——发现后除漏洞工单外，抄送财务对账线索（对账篡改同此，见 R-SC-03）；测试产生的积分与抵扣要清理并记录清理单号。

**【AI 位】** AI 写积分流水平衡校验脚本（每账户期初期末守恒检查），跑测试期间全部流水找断点；断点定位脚本可直接转成第六章的 check。

### 2.3 退款链

退款链是交易链的逆向链：正向的每一处"信任客户端"，逆向都会再暴露一次；且逆向叠加了"渠道校验、库存回补、促销冲销"三个新面。**所有退款类生产测试必须使用可撤销订单与沙箱渠道**（第三章 3.3）。

#### R-RF-01 退款金额篡改

**【原理】** 退款金额来源错误：退款请求回传 `refundAmount` 被直接采用，或退款额从可被前置步骤修改的订单快照读取。第三方支付渠道会校验"退款 ≤ 原流水金额"，但**退到企业钱包/余额/储值卡**的路径常缺这层渠道校验——渠道是漏斗的最后一段，不是全部。

**【测试方法】** ①退款请求改 `refundAmount=实付×2`；②部分退款金额改超"剩余可退"；③换退款路径：原路退改退余额、余额与储值卡互转（渠道校验绕过的常见缺口）；④退款币种/账户类型字段篡改（积分退成现金类）。

**【验证】** 退款受理成功且金额 > 实付（或 > 剩余可退），钱包/储值到账与流水一致即实锤。测试推进到"受理成功+到账记录"即停，立即走撤销或测试渠道对冲。

**【修复】** 退款金额 = 服务端订单实付快照计算，客户端金额字段一律忽略；渠道退款与余额退款双路径统一上限校验；币种/账户类型服务端白名单。

**【陷阱】** ①生产退款测试必须用测试商户沙箱渠道+可撤销单（VOL-10 第六幕的沙箱单纪律）；②"单次无害 ≠ 累计无害"——接着做 R-RF-02 的累计测试才能下结论；③退款接口常挂风控（异地、频次），拦截与校验要分开归因。

**【AI 位】** AI 枚举退款接口全字段并标注三类可控字段（金额/路径/原因），生成篡改矩阵与预期结果表；余额类路径标"渠道校验缺失候选"。

#### R-RF-02 部分退款累计超限

**【原理】** "剩余可退金额"未锁定：每次部分退款只校验"本次 ≤ 实付"，不校验"累计 + 本次 ≤ 实付"。多次小额退款累计穿透实付上限。与 R-TX-03 同构——库存扣减的非原子性在资金侧的镜像。

**【测试方法】** 同一订单连续发起 3 次以上部分退款（每次金额均小于实付，如实付 100 元退 60/60/60），逐次记录"剩余可退"变化；间隔提交与并发提交两个形态都测（并发版=资金侧超卖）。

**【验证】** 累计退款额 > 订单实付即实锤；停止受理的那一次就是校验逻辑的边界——把边界值也记入证据（修复验证要用）。

**【修复】** 退款以"实付 − 已退"为分母的原子扣减（数据库行锁或唯一约束），与 R-TX-03 的库存原子扣减同一工程解法。

**【陷阱】** ①连续退款触发风控异常退款模型后账号被冻结，易误判"已修复"——区分风控拦截与业务校验（响应体特征不同），必要时在关闭风控开关的测试环境复测；②每次退款都要记可撤销凭证，收尾统一对冲。

**【AI 位】** AI 生成"累计边界"测试序列表（实付 100：60/60/60、55/55/55…的设计理由），并从退款响应归纳拦截方（风控/业务/渠道）特征字段对照表。

#### R-RF-03 退款不退货（仅退款滥用）

**【原理】** 仅退款流程与实物回流未绑定校验：申请仅退款不要求物流单号、不校验收货状态门槛，或小额订单在客服审核阈值内自动秒退。收货后申请"未收到货"类仅退款即可套货。这是**业务规则与流程设计**的混合缺陷，不是纯技术漏洞。

**【测试方法】** 已签收订单申请仅退款（原因选"未收到货"类），观察三件事：①是否要求物流凭证/照片；②小额是否自动秒退（找自动退款阈值）；③收货状态与退款资格是否关联（改状态字段或从待收货态发起）。

**【验证】** "款退、货未回"成立：订单退款成功且无退货物流、无库存回补，即流程缺陷实锤；自动秒退路径单独记录（阈值+条件）。

**【修复】** 仅退款资格与订单状态机绑定（签收后仅退款转人工+凭证要求）；自动退款限额与频次双风控；套货特征进风控名单。

**【陷阱】** ①部分品类（生鲜、定制、临期）"仅退款"是**合法业务流程**——先与业务确认规则再定性，否则必被"这是 feature"顶回（第五章 5.5）；②测试用自己下的测试单，货款留在测试账户不提现；③这类发现的修复常在业务规则侧（阈值调整），技术复测之外要业务确认。

**【AI 位】** AI 把"退款类型 × 订单状态 × 处理路径（自动/人工/拒绝）"整理成判定矩阵，标出自动通过的组合格——矩阵即漏洞面热力图。

#### R-RF-04 库存·资金双线不一致

**【原理】** 退款事务未覆盖库存线：退款成功但库存未回补（少卖），或未退货退款却回补库存（虚增）；资金流水与库存流水分属两个服务，无对账兜底。生态形态下，"事务"横跨订单/库存/支付/促销四个中心，分布式一致性靠编排（Saga/消息最终一致），每一步补偿缺失都是断点。

**【测试方法】** 全链对账实验：下单 → 支付 → 取消/退款，每一步同时记录四元组（订单状态、库存值、资金流水、积分流水），退完后做期初期末守恒比对。三个变体都要跑：未支付取消、已支付未发货退款、已签收退货退款。

**【验证】** 任一线不一致即实锤：资金退了库存没回、库存回了资金没退、积分/优惠券没冲销。守恒式：`库存变化 == 成交-取消-退款回补`、`资金净额 == 支付-退款`。

**【修复】** 退款编排事务化（Saga 可，但每步要有补偿与对账断点）；T+1 对账任务覆盖订单-库存-资金-积分-券五方，差异自动告警。

**【陷阱】** 异步最终一致是常态：秒级延迟 ≠ 漏洞——设观察窗（如 5 分钟）后再判，报告里写明观察窗口与判定时点；T+1 对账兜底的存在会把定级拉低（有兜底的资损是"少赚"，无兜底才是"失血"）。

**【AI 位】** AI 写四线对账脚本（每步四元组快照+期末守恒校验），这是场景库自动化优先级最高的 check 之一（第六章 6.2）——手动做一遍的价值在于为脚本定义正确的守恒式。

### 2.4 会员链

#### R-MB-01 会员等级越权

**【原理】** 等级权益的服务端二次校验缺失：等级字段客户端可控（请求携带 `memberLevel/gradeId` 且被采信），或权益核发接口只校验"有券资格"不校验"等级够"。黑盒形态：V0 账号的请求里带 V6 标识，专属价/专属券照发。

**【测试方法】** ①注册新号（V0），在下单/领券/权益接口把 `memberLevel` 改 V6 重放；②用 V0 的 token 直接调高等级专属接口（专属价 SKU 下单、专属券领取、免邮权益）；③等级字段多层位置都试：请求体、Header 里的会员信息、埋点透传字段。

**【验证】** V0 账号以专属价成交或专属券到账，且会员中心的等级记录未变——"记录未变 + 权益已发"的矛盾即实锤。区分**展示层泄露**（前端可见 V6 价）与**成交层越权**（真按 V6 价成交），两者定级差两档。

**【修复】** 等级一律从会员中心会话/服务端查询取，请求中的等级字段忽略；权益核发前服务端二次校验等级。

**【陷阱】** 专属价展示泄露单报（低危信息泄露），成交越权单报（资损）——混在一张单里开发只会修展示层；等级权益常配置在规则引擎，复测时要确认规则侧也收紧（第五章 5.4 复测纪律）。

**【AI 位】** AI 汇总"等级门控接口清单"（响应含 level/grade/rights 字段的接口），生成 V0 账号重放用例集与预期结果表。

#### R-MB-02 权益冒领（重放与横向）

**【原理】** 权益领取的两个缺口：①幂等缺失——生日礼/新人礼/回归礼可重放多领；②主体错位——领取接口携带 `targetMemberId`，可为他人代领（消耗他人资格、权益却落到自己账上，或反之）。与 VOL-02 1.1 的 IDOR 同构，对象换成"权益资格"。

**【测试方法】** ①重放新人礼领取接口 3 次（间隔与连发两形态）；②改 `targetMemberId` 为自己控制的另一测试账号，观察"资格消耗方"与"权益到账方"是否分离；③跨端领取：App 领过的小程序再领（多端幂等缺口）。

**【验证】** 同一权益多份到账、或 B 的资格被 A 的请求消耗、或跨端重复到账——任一成立即实锤，以权益流水为口径。

**【修复】** 领取幂等（会员 × 权益类型 × 周期 唯一约束）；资格与到账同主体校验（服务端会话主体 == 权益落账主体）。

**【陷阱】** 横向测试**只用自己控制的双账号**——对生产真实会员 ID 发起领取请求，即使失败也构成对他人账户的写入尝试（PIPL 红线 + 内部红线，第三章 3.2）；"资格消耗在对方、到账在自己"是最严重形态（资损+他人损害），发现即停，不扩大样本。

**【AI 位】** AI 归纳权益接口的"主体字段表"（身份从 token 来还是从参数来），标出参数化主体字段；跨端幂等缺口要 AI 按"端 × 权益"生成矩阵用例。

#### R-MB-03 注销残留

**【原理】** 注销链路不完整：注销后手机号可重新注册并**继承**原账户数据（订单历史/等级/积分/欠款）；注销未吊销全端 token、未解绑第三方（联合登录/支付授权）；"删除"只是账号表打标记，数据域没动。同时构成 PIPL 删除权（第 47 条方向）的控制缺失——技术漏洞与合规发现双轨。

**【测试方法】** ①测试账号 A 注销 → 同手机号重新注册 → 比对新账户可见数据（订单/积分/等级/地址/第三方绑定）；②注销后用旧 token 调会员接口（多端各试：App/小程序/Web）；③第三方登录账号注销后再绑定；④注销前挂一个在途订单/未冲销积分，看注销是否被阻止。

**【验证】** 新账户看到 A 的残留数据、旧 token 仍有效、第三方可再绑定——任一成立即实锤；合规侧按"删除权控制缺失"另行登记（第三章 3.5 写法）。

**【修复】** 注销 = 数据按分类执行（可识别个人信息删除/匿名化，交易凭证按会计与税法要求留存）+ 全端 token 吊销 + 第三方解绑闭环 + 重注册不复活旧主体。

**【陷阱】** "删除"与"留存"有法定边界：交易凭证的留存是会计/税法义务——报告引法规要准确（删的是可识别个人信息，不是全部数据），过度主张会被合规部退回（第三章 3.5 反面清单）。

**【AI 位】** AI 生成注销核对清单（会员数据域 × 应删/应匿名/应留存三态），跑一遍数据域清单式核查；三态判定规则先由你与合规接口人确认，AI 只做枚举与执行。

### 2.5 供应链链

供应链链在后台层，测试对象是**内部员工与外部供应商租户**的双面系统。三个场景的共同前置：测试供应商账号要走内部申请流程提前办妥（第五章 5.2），采购单据全程在草稿/测试流程内推进。

#### R-SC-01 供应商门户横向越权

**【原理】** 多租户隔离缺位：门户登录态只认证"是供应商"，未绑定"是哪家供应商"；对账单/送货单/发票接口的 `supplierId` 来自请求参数。等价于 VOL-02 1.1 的 IDOR 租户版——审计视角即"每条查询少了租户条件"。

**【测试方法】** 两家测试供应商账号 A/B：A 的会话携带 B 的 `supplierId` 逐个请求对账单/送货单/发票/结算接口；无第二账号时改 `supplierId±1` 只做**存在性验证**（看报文结构变化，不翻页拉数据）。

**【验证】** A 会话返回 B 的单据（供应商名称、银行尾号等标识变化）即实锤。证据最小化：一张脱敏截图足够，**不导出、不分页枚举**。

**【修复】** `supplierId` 从会话/租户上下文取，参数中一律忽略；接口层统一租户过滤（审计语境：租户条件进公共中间件，不靠每个 SQL 自觉）。

**【陷阱】** ①供应商是外部法人主体：数据泄露涉及对供应商的通知义务，发现即走高危上报（第五章 5.6），**不扩大验证范围**；②存在性验证时若遍历参数，每次只改一个值、看响应结构，绝不批量拉取——"能证明可达"就是全部目的。

**【AI 位】** AI 从门户全功能抓包提取"租户标识字段分布表"（哪些接口带 supplierId/vendorId/tenantId），生成横向对照用例清单。

#### R-SC-02 采购审批绕过

**【原理】** 审批流的状态与权限双缺陷：审批接口不校验"当前操作者是否本节点负责人"（越级/替代审批）；或单据状态推进接口无权限门槛，申请人自己把单据推到"已审批"。内控视角：不相容职务未分离（申请与审批同一人可完成全流程）。

**【测试方法】** ①申请人账号直接调审批通过/驳回接口（approve/reject 路径）；②普通审批人调"终审"节点接口；③并发双审批（同节点两人同时批，看是否重复推进或重复通知）；④改请求中的 `nodeId/approver` 字段越位。

**【验证】** 单据状态被非法推进到下一节点（单据流水的操作者记录 + 消息通知为证）即实锤；并发重复推进单独记录。

**【修复】** 审批动作 =（节点负责人会话 + 当前节点状态 + 动作类型）三元组校验；状态机表驱动——与 R-TX-04 同一工程解法，换个业务域。

**【陷阱】** 生产采购单是真实业务单据：全程在**自建草稿单/测试流程**内推进，绝不动他人单据；审批动作会触发真实审批人的消息通知——选自己团队的测试单，提前知会（流程越界也是越界，第五章 5.2）。

**【AI 位】** AI 从抓包还原审批流图（节点 × 角色 × 动作 × 状态迁移），圈出"无校验候选边"；你按图逐边验证，图入报告。

#### R-SC-03 对账数据篡改

**【原理】** 对账单的金额/数量来自客户端回传：供应商确认对账接口提交明细行（数量/单价可改），或对账快照生成后仍可被重放修改；确认后无二次复核直接进入结算。资金链终端的"最后一公里校验"缺失。

**【测试方法】** ①确认对账请求改一行数量（+10）提交；②同一对账单重复确认（幂等）；③确认后再次拉取对账单比对快照是否可变；④确认接口的附件/凭证替换（对账依据被换）。

**【验证】** 确认后结算侧单据反映篡改值、或重复确认产生多份结算单即实锤。

**【修复】** 对账明细服务端从收货/入库单据生成，客户端只传"确认"不传明细；确认幂等+确认后只读；结算前二次复核钩子。

**【陷阱】** ①内控类发现的定级不走 CVSS 而走**内控影响尺**（资金错配上限 × 可及性），报告两把尺并列（第三章 3.5、VOL-07-08 B3）；②测试篡改的对账单必须在结算触发前撤销/作废，撤销凭证留档。

**【AI 位】** AI diff 对账接口的"提交明细字段"与"服务端明细字段"重合度——重合度越高，客户端可篡改面越大；输出字段级重合度表。

| R-TX-03 | 并发超卖 | 交易 | 库存校验/下单 | 库存（超卖） | 非原子 |
| R-TX-04 | 订单状态机绕过 | 交易 | 状态接口/支付回调 | 资金+货物 | 状态机/验签缺失 |
| R-PX-01 | 券生成·叠加·复用·转赠 | 促销 | 领券/核销/转赠 | 营销资损 | 幂等/原子缺失 |
| R-PX-02 | 满减顺序与优惠分摊 | 促销 | 下单+退款两端 | 资金（多退） | 双实现失配 |
| R-PX-03 | 秒杀资格与库存 | 促销 | 秒杀下单路径 | 营销资损 | 资格非原子 |
| R-PX-04 | 积分汇率与转移 | 促销 | 抵扣/转赠 | 负债（积分） | 信任客户端+非原子 |
| R-RF-01 | 退款金额篡改 | 退款 | 退款接口/退款路径 | 资金（多退） | 信任客户端 |
| R-RF-02 | 部分退款累计超限 | 退款 | 部分退款 | 资金（多退） | 非原子 |
| R-RF-03 | 退款不退货 | 退款 | 仅退款申请 | 货物 | 流程设计缺陷 |
| R-RF-04 | 库存资金双线不一致 | 退款 | 退款编排全链 | 库存+资金 | 分布式一致性 |
| R-MB-01 | 等级越权 | 会员 | 权益/专属价接口 | 营销资损 | 二次校验缺失 |
| R-MB-02 | 权益冒领 | 会员 | 权益领取接口 | 营销资损+他人损害 | 幂等+主体错位 |
| R-MB-03 | 注销残留 | 会员 | 注销/重注册 | 合规+数据泄露 | 删除链路不完整 |
| R-SC-01 | 供应商门户横向越权 | 供应链 | 门户对账/单据接口 | 数据泄露（对外部主体） | 租户隔离缺位 |
| R-SC-02 | 采购审批绕过 | 供应链 | 审批/状态接口 | 内控失效 | 权限+状态机 |
| R-SC-03 | 对账数据篡改 | 供应链 | 对账确认接口 | 资金（错配） | 信任客户端 |

**矩阵的用法与边界**：矩阵是**下界不是上界**——负空间思想（VOL-09C ⑨）：未列入的组合（如"积分 × 秒杀 × 退款冲销"三元组合、POS 端 × 会员链）是下一轮场景孵化区。每轮交战结束时，把新发现但不在库内的场景补录进场景库并编号——场景库是要生长的账本。

## 第三章 支付与合规红线

> 🧭 **导读**：一人红队的红线写在授权书里；企业内部的红线还有第二层——法规与行业标准。本章三份"负面清单"：PCI DSS 对卡数据、PIPL 对个人信息、内部环境策略对生产数据，外加敏感数据处置流与合规类发现的报告写法。审计类比：这章相当于"职业道德与独立性准则"——不是能力章，是**资格章**；踩线一次，你后面的所有发现都会被质疑取证合法性。

### 3.1 PCI DSS 基础与卡数据链路

PCI DSS 是支付卡产业公开发布的数据安全标准（PCI SSC），约束**存储、处理、传输持卡人数据**的实体。零售企业的常见形态：线上支付走持牌支付渠道/聚合支付（企业系统不碰完整卡数据的，适用范围大幅缩小，SAQ A 类自评场景）；POS 自营收单、柜面手输卡号、电话订单记卡（MOTO）则把企业拉回完整适用范围。渗透工程师不需要背全部条款，需要背的是**卡数据元素的存与不存**：

| 卡数据元素 | 授权后能否存储 | 零售生态里常出现在哪 | 渗透红线 |
|---|---|---|---|
| PAN（主账号） | 可存，但须截断或加密并配套密钥管理 | 订单表、客服系统、日志、小票、回调报文 | **能看不能存**：证据打码截断，不复制原始值 |
| CVV/CVC（安全码） | **任何情况下不得存储** | 支付请求瞬时经过、客服录音（客户念卡）、POS 输入缓存 | **绝不构造含 CVV 的测试请求**；发现存储立即上报 |
| 磁道/芯片等效数据 | 不得存储 | POS 内存转储、读卡器驱动日志、异常诊断包 | **只证存在，不提取内容**（记录位置与样本量即止） |
| 有效期 | 可存（非敏感认证数据） | 订单/风控字段 | 常规脱敏即可 |
| PIN/PIN 块 | 仅加密形态（若业务合法持有） | 收单链路 | 不碰，发现明文立即上报 |

碰卡三原则（背下来）：**能看不存、CVV 绝不测、磁道只证存在**。

**卡数据链路速览**（一图看清卡数据在零售系统哪里出现、以什么形态出现）：

```
POS 磁道/芯片读卡 ──┐                        ┌── 渠道侧（持牌机构）
收银台手输卡号 ─────┼──→ 支付中心 ──加密通道──┤
电话订单记卡(MOTO) ─┘          │              └── 异步回调 ──→ 支付中心/订单中心
                               │                                │
                      日志与报文落盘点                  对账文件 / 客服工单 / 录音转写
              （高危：明文 PAN/CVV 随日志留存）      （高危：明文留存、邮件附件流转）
```

链路上的四个观察点：①读卡瞬间——磁道数据只在这一段完整存在；②支付请求瞬时经过——CVV 只应瞬时出现、不留任何缓存；③回调与日志落盘——**最常见的违规存储点**（回调报文全量进日志）；④对账与客服侧——卡数据的二次扩散点（对账文件、念卡录音转写）。渗透巡检沿这四点布防，证据采集口径回到三原则。

**卡数据泄露的高发位置清单**（公开知识层面的检查点，测试时按清单巡）：支付回调与通知日志全量落盘（含完整卡号）、客服系统明文记录念卡录音转文字、POS 小票打印完整 PAN（截断规则未配）、测试/预发环境用生产卡数据跑批、错误堆栈把请求体带进日志平台、对账文件以邮件明文附件流转。

**发现存储违规的处置**：停止深挖 → 最小取证（记录位置、样本计数、一张重度脱敏截图，**不复制数据本体**）→ 高危上报（第五章 5.6，同时知会卡数据 Owner）→ 由 Owner 决定清除与是否触发合规评估。你的角色终止于"证明存在与位置"。

### 3.2 PIPL/个保法对测试的约束

个人信息保护法是公开法律文本，对渗透动作的约束按"法条方向 → 测试纪律"翻译：

| PIPL 方向（公开要点） | 对测试动作的落地纪律 |
|---|---|
| 最小必要（第 6 条方向） | 越权验证用自产测试数据或授权样本；不遍历拉取真实客户数据——验证终点是"可达"，不是"数清有多少" |
| 目的限制 | 测试中获得的个人信息只用于证明漏洞存在，不二次分析（不做画像、聚类、导出留用） |
| 敏感个人信息严格保护（第 28/29 条方向：单独同意等） | 人脸/身份证/银行卡字段验证止于"能访问"：响应体不落盘、截图重度脱敏、样本即弃 |
| 删除权/注销（第 47 条方向） | R-MB-03 类发现同时按合规发现双轨登记（3.5 写法） |
| 委托处理与对外提供限制 | 测试数据不出生态：不进外部 AI、不打包带出办公环境（第五章 5.8） |
| 影响评估义务（第 55/56 条方向） | 大规模数据处理系统的测试发现，报告中提示业务侧评估义务的存在，不替业务下结论 |

**测试账号纪律**（四条，缺一不可）：①专用测试账号、数据自产（虚构姓名/地址/手机号走测试号段）；②不用生产真实客户账号——哪怕业务方递给你"就用这个账号看"；③确需真实样本时走授权流程，拿脱敏副本并登记；④凭据进 `creds.yaml` 管理（VOL-09C ⑤），不进聊天记录、不进 AI prompt。

### 3.3 生产 vs 测试环境策略与数据最小化

| 环境 | 定位 | 测试策略 |
|---|---|---|
| SIT/功能测试 | 首选：逻辑全量可测，数据全假 | 五链 18 场景全量过账；并发/篡改类先在这里定机制 |
| UAT/预发 | 接近生产配置 | 先问清**数据来源**——预发接生产数据影子库的，按生产纪律对待 |
| 生产 | 护栏内存在性验证 | 四护栏（下表）齐备才动手 |

生产测试四护栏：**低峰窗**（业务方确认时段）、**限额**（并发数、请求次数、影响 SKU 数上限）、**可回滚**（沙箱支付渠道、可撤销单、可恢复状态）、**报备**（值班安全 + 业务 Owner 知会，紧急联系人写进交战单）。

数据最小化技巧：收货信息用"测试+公司收货点"；金额边界用低价 SKU 与 1 分钱测试商品；报文落盘前过脱敏过滤器（VOL-07-08 B4 的证据脱敏规范）；原始流量加密留存、限期清理（第五章 5.7 留存策略）。

### 3.4 发现敏感数据泄露的处置流

| 步骤 | 动作 | 禁止 |
|---|---|---|
| ① 发现 | 判定类别：卡数据/个人信息/商业策略 | 继续扩大验证范围 |
| ② 止血 | 停止深挖；如接口可及性已被证明，撤出 | 尝试"看看能拉多少" |
| ③ 取证 | 最小样本：位置 + 计数 + 一张脱敏截图 | 复制数据本体、导出列表 |
| ④ 上报 | 高危通道（第五章 5.6），卡数据与个信类同时知会合规接口人 | 在群里贴明文截图 |
| ⑤ 配合定级 | 数据分级 × 量级 × 可及性；提供事实 | 替业务下"是否需监管报告"的结论 |
| ⑥ 记录 | 交战日志留痕：发现时刻、动作序列、处置结论 | 只口头报告不留痕 |

一句话版：**验证的终点是"证明可达"，不是"数清有多少"**。

### 3.5 报告里合规类发现怎么写

合规类发现与技术漏洞的差异，从标题到责任方都不同：

| 维度 | 技术漏洞发现 | 合规类发现 |
|---|---|---|
| 标题句式 | "XX 接口存在价格篡改导致资金损失" | "XX 系统存在卡数据存储行为，不符合 PCI DSS 要求 3 方向的存储控制" |
| 证据 | 请求/响应/复现步骤 | **位置与样本计数**，不含数据本体 |
| 定级 | CVSS + business_impact（VOL-07-08 B3） | 内部数据分级为主、CVSS 为辅或并列 |
| 责任方 | 开发团队 | 数据 Owner（含合规接口人） |
| 整改 | 技术修复 | 流程 + 技术 + 制度三线 |

**例文（虚构）**：

> 【合规类发现】客服工单系统（`ticket.nanhua.example`）的通话记录转写字段中存在客户口述完整卡号与安全码的明文留存。抽样观测 3 条记录即可确认字段存在（样本截图已脱敏，未复制数据本体）。该行为不符合"授权完成后不得存储敏感认证数据"的公开标准要求，建议：①立即清理存量并关闭转写留存开关；②排查同类字段；③由卡数据 Owner 评估是否触发进一步合规流程。

**反面清单**（写合规发现的四种死法）：①贴 PAN/CVV 截图——证据本身违规；②写"约 XX 万条客户数据受影响"——没有授权的精确统计就是编数字；③替业务下"需要监管报告"的结论——那是合规部的职责，你提供事实；④引法条引到具体款项却引错——引到条/款方向即可，拿不准就只写原则。

## 第四章 SSO 与账户生态攻击面

> 🧭 **导读**：零售企业三类人——员工、会员、供应商——三套身份体系，中间用联邦协议（OIDC/SAML/CAS 等公开标准）缝合。账户生态是生态渗透的"总开关"：拿下一条身份边界的混淆，等于同时靠近 OA、邮箱、VPN 和会员资金账户。VOL-02 讲过 OAuth 的单点漏洞，本章讲它们在多端零售生态里的**组合形态**。审计类比：这相当于集团的**关联方交易**审计——每笔交易单独看都合规，拼起来看资金流向才发现问题；每个 SSO 配置单独看都没错，拼起来看信任链才发现断点。

### 4.1 三类身份与联邦登录

| 身份域 | 主体与来源 | 凭据形态 | 常见入口 | 关键风险 |
|---|---|---|---|---|
| 员工域 | HR 主数据 + 目录服务（AD/LDAP 类）→ 内部 SSO | 账号密码 + MFA（各系统强弱不一） | 内部门户、OA、邮箱、VPN、运维平台 | 内网横向的起点（VOL-03）；MFA 覆盖不全的系统是短板 |
| 会员域 | 会员中心（手机号注册/一键登录/第三方联合登录/匿名会员） | token、手机号+验证码、第三方授权 | App、小程序、Web、POS 会员识别 | 资金（钱包/积分）与个人信息的直接载体 |
| 供应商域 | 门户账号（企业开通、生命周期靠人工） | 账号密码为主，MFA 少见 | 供应商门户 | 多租户越权入口（R-SC-01）；离职人员账号残留 |
| 联邦层 | OIDC/SAML/CAS 等公开协议连接以上各域 | 断言、code、token | 统一登录页 | 协议实现缺陷是跨域跳板；单点失效=全域失效 |

三域各自的"最弱入口"决定整体水位：员工域看 VPN 与老系统、会员域看验证码与一键登录、供应商域看密码策略与账号回收。

### 4.2 OAuth/OIDC 六攻击面（生态组合形态）

VOL-02 与 VOL-07-08 的方法论在此适用；下表是零售生态的组合形态与特有陷阱：

| # | 攻击面 | 原理一句话 | 测试动作 | 验证判据 | 生态特有陷阱 |
|---|---|---|---|---|---|
| ① | redirect_uri 篡改 | 校验只做前缀/子串匹配，可接外部回调 | 逐级变造：子路径、`@`、编码、大小写、末尾斜杠 | 授权 code 落到攻击者可控页 | 三端（App 深链/Web/小程序）共用 client_id，白名单常过宽 |
| ② | state 缺失与 callback 注入 | 无 state 防 CSRF，回调可被注入绑定他人身份 | 走完整码流，检查 state 是否存在且校验；构造跨账号回调 | 无 state 下完成账号绑定/登录 | 生态内多 RP（依赖方）接入，一个 RP 松全链松 |
| ③ | token 泄露路径 | token 进 URL/fragment → Referer、日志、埋点 | 检查授权后跳转 URL、埋点上报字段、会话存储过期配置 | token 出现在日志/上报/Referer 任一处 | **埋点 SDK 全 URL 上报**是零售特有高发点——分析平台是第三方域 |
| ④ | 会话不注销 | RP 未实现单点登出，token 无撤销 | 登出后重放旧 token/断言（多端各试） | 登出后旧 token 仍可用 | 员工离职禁用 SSO，但会员 App/第三方绑定的旧 token 还活着——身份域传导 |
| ⑤ | 多端权限模型断层 | 同一账号在 App 新版/小程序旧版/POS 的接口权限不同 | 同一 token 在多端重放同一接口，比对权限差异 | 旧端接口未收紧（高危操作通过） | 版本碎片化：旧接口因"还有老版本用户"不能下线，形成永久侧门 |
| ⑥ | 域边界混用 | 员工 SSO 与会员开放平台的 callback/作用域混用 | 员工 token 打会员侧高权接口；会员 token 打内部接口 | 任一方向通过即实锤 | 内部员工折扣客户端"一套 token 两种身份"，上下文切换处最易混 |

### 4.3 身份矩阵：测试纪律与账号准备

身份域测试的账号矩阵（VOL-09C ⑤ 身份矩阵思想在生态形态的扩展）：

| 账号 | 域 | 角色 | 用于 |
|---|---|---|---|
| E-1 | 员工 | 普通员工 | 基线；⑥域边界测试 |
| E-2 | 员工 | 管理员（测试岗） | 垂直越权对照（VOL-02 1.2） |
| M-1/M-2 | 会员 | V0 新号 ×2 | R-MB 链、横向冒领（双号对照） |
| M-6 | 会员 | 高等级（测试配置） | 等级门控对照 |
| S-1/S-2 | 供应商 | 两家测试供应商 | R-SC-01 横向越权 |

纪律三条：①矩阵账号全部自产/测试配置，凭据入 `creds.yaml`（0600、gitignore）；②token 样本不落明文，引用走占位符（VOL-09C ⑦）；③矩阵先行——没有对照账号的"越权发现"提单会被复测打回。

### 4.4 内部系统与会员体系的边界

两类最常见的边界混淆（审计语境：关联方之间资金往来未识别）：

| 混淆形态 | 后果 | 测试要点 |
|---|---|---|
| 员工身份"借用"会员接口：内部折扣、员工价、内购通道用员工 token 走会员体系 | 员工 token 在会员侧获得资金权限（钱包/积分），两套权限模型不一致处即断点 | 身份矩阵 E-1 × 会员资金接口全量差分（4.2 ⑥的具体化） |
| 会员开放平台"蹭"内部信任：第三方应用授权拿到过宽 scope，或回调地址指向内部系统 | 外部应用可调内部接口，数据经开放平台外流 | 第三方应用的 scope 声明与实际可调接口清单逐项对照 |

边界原则一句话：**员工域、会员域、供应商域各有各的钱和数，任何跨域 token 都应按"降级到最弱域"处理**——跨域调用要么显式声明（scope 白名单逐项），要么就该被拒绝；"历史原因打通的"通道是边界测试的第一站。

## 第五章 企业内部渗透工作流（与一人红队的差异）

> 🧭 **导读**：一人红队的交付物是一份报告；企业内部的交付物是"被修复的漏洞 + 可审计的过程"。工作流从战役制变成常态制，你面对的不再是客户的系统，而是**发布节奏**——每个版本上线前哪些链路必须过、哪些场景可以抽测。审计类比：从年审项目制变成内审常态化——立项、底稿、复核、整改跟踪四件事天天做，本卷第二章场景库就是你的"审计程序表"。

### 5.1 形态差异总表（工作流视角）

### 5.2 内部授权形态与 scope 变更流程

**双层授权结构**：常态授权池（团队与各业务域签的年度测试框架，界定"哪些系统域常年在册"）+ 交战 scope 单（每轮交战的具体系统、环境、时间窗、动作白名单、护栏、紧急联系人）。授权单要素表：

| 要素 | 内容 | 常见坑 |
|---|---|---|
| 系统 | 交战系统清单（对应 inventory/systems.yaml） | 只写前台域名漏掉中台服务——按数据流归并业务域授权 |
| 环境 | SIT/UAT/生产分别列 | 预发接生产数据的要显式标注纪律 |
| 时间窗 | 起止日期 + 生产低峰时段 | 窗口外"补测"= 无授权测试 |
| 动作白名单 | 允许的测试类型（重放/并发上限/篡改类） | 并发上限、请求量上限写成数字 |
| 护栏 | 数据最小化要求、可回滚手段、知会对象 | 引用第三章红线清单作为附件 |
| 紧急联系人 | 值班安全、业务 Owner、合规接口人 | 高危上报流的入口（5.6） |

**scope 变更流程**（测绘发现影子资产后的标准动作）：发现 → 资产归属确认（问资产管理/安全平台："这个域名是谁的"）→ Owner 书面同意（IM 记录不算，要邮件或平台单）→ scope 增补进 scope.yaml（版本化，变更记录进交战日志）→ 才允许第一个测试请求。**跨系统关联测试的归并**：下单链涉及网关→订单→促销→支付→会员五个系统，逐个找五个 Owner 会拖死节奏——按"数据流归属"申请业务域级授权（例：交易域），域内服务自动在册。

### 5.3 商业工具与内部平台联动

| 工具/平台 | 在生态形态里的位置 | 与你的组合拳 |
|---|---|---|
| Burp Pro 等商业套件 | 手工逻辑测试主力（VOL-06 工具链） | 五链场景全手工段 |
| 内部 DAST/爬虫平台 | 攻击面清单的例行维护 | 你用它的产出做入口发现，它测不了业务逻辑 |
| SAST 平台 | 提交前代码扫描的告警池 | **你的差异化优势**：SAST 告警"金额字段来自请求参数"对黑盒选手是天书，对你直接转成 R-TX-01/R-RF-01 的验证用例（源码联动，VOL-04） |

灰盒常态的心法：**每个 SAST 污点告警都是一条免费的"代码路标"**——你 5 年源码审计的读解能力，把它从"误报池"变成"逻辑漏洞线索池"。

### 5.4 漏洞提单规范与 JIRA 复测流

提单字段表（findings 契约的内部形态，字段语义对齐 VOL-09C ⑧）：

| 字段 | 要求 | 反例 |
|---|---|---|
| 标题 | 系统 + 场景编号 + 一句话 | "订单有问题" |
| 环境 | 环境、版本号/发布号 | 不写版本——复测时系统已升级 |
| 复现步骤 | 可独立重放的步骤序列（POC 卡规范，VOL-07-08 B2） | "见聊天记录截图" |
| 证据 | 脱敏后的请求/响应/流水 | 明文 PII、真实 PAN |
| 影响 | 资损方向 × 量级估算 × 前置条件 | 只写 CVSS 分数不给业务影响 |
| 修复建议 | 指向场景库的【修复】段 | "建议加强校验" |
| 复测条件 | 需要的测试账号、环境、数据 | 复测时才现要账号 |
| scope 确认 | 本发现可证明在授权范围内（in_scope_confirm） | — |

复测状态机与四态判定：新建 → triage（安全+开发联合定性）→ 修复中 → 提测 → **渗透复测** → 判定（已修复/部分修复/未修复/风险接受，须书面确认，VOL-07-08 B6）→ 关闭。

内部定级参考（资损尺与通用尺并列，business_impact 优先于 CVSS）：

| 级别 | 资损尺（业务影响判据） | 典型场景 |
|---|---|---|
| 高 | 资金可增发 / 可批量多退 / 外部主体数据泄露 | R-RF-01、R-SC-01、支付回调伪造（R-TX-04 变体） |
| 中 | 有条件资损（需登录 / 多步 / 有风控兜底） | R-TX-01、R-PX-02、R-MB-01 成交形态 |
| 低 | 展示层泄露 / 精度误差 / 单点无害 | 专属价展示泄露、±0.01 分摊误差 |

分级时同时标注"依赖风控兜底"与否——同样的多退漏洞，有 T+1 对账兜底与没有，定级差一档（R-RF-04 陷阱②）。

**复测纪律**：复测不是"重跑一遍原 POC"——要验证修复没有引入新洞。价格改成服务端重算了，就要接着测 R-TX-02 数量与 R-RF-02 累计（同一个算价函数的相邻入口）；"风险接受"必须有业务 Owner 书面确认与接受期限，进台账定期复审。

### 5.5 与开发的沟通术："这是 feature 不是 bug"怎么办

| 场景 | 对方说法 | 你的应对 |
|---|---|---|
| 定性之争 | "这是 feature，业务就这么设计的" | 先查业务规则文档/找产品确认：真是 feature → 转风险登记（业务 Owner 签字接受，进台账）；不是 → 用资损量化说话（单笔上限 × 频次上限 × 可及性） |
| 环境之争 | "测试环境有，生产没有" | 求同存异：测试环境固化机制证据，生产做无害存在性验证，报告标注"环境差异待生产复核" |
| 依赖之争 | "风控会拦住的" | 把"风控拦截"和"业务校验"分开验证（关风控开关的测试环境跑一遍）；报告写明"该风险依赖风控兜底而非业务校验"的架构性风险 |
| 优先级之争 | "排不上，下个迭代吧" | 用 business_impact 字段说话（资损方向 × 上线窗口），交平台分级仲裁，不私下拉扯 |
| 归属之争 | "这是中台的问题不是我们组的" | 附调用链证据（inventory/systems.yaml 的路由映射），归属判定交 triage |

三条原则：**技术争议找数据**（对照实验与报文证据）、**定性争议找 Owner**（业务规则谁定谁裁）、**优先级争议找平台**（分级机制）。你只对"事实与证据"负责——这既是沟通策略，也是自我保护。

### 5.6 高危紧急上报流

触发判级参考（三要素叠加即最高级）：**资金可增发**（退款篡改/积分凭空/券多领）、**外部可及**（公网接口、无需登录）、**批量可及**（越权可遍历）。

流程：**即时通道**（电话 + 安全值班群，15 分钟内，先口头后补文字）→ **止血建议**（接口限流/临时下线/WAF 规则/功能开关——你比任何人都清楚攻击路径，止血建议是你的高光时刻）→ **2 小时书面速报**（现象/影响面/证据/止血建议/下一步）→ **24 小时正式工单** → 复盘进知识库与场景库（新场景补录编号）。涉及外部主体数据（供应商/客户批量）时同步合规接口人——通知义务的时钟从发现时刻开始走。

### 5.8 【AI 位】企业内 AI 使用的数据边界红线

VOL-09C §4.3 的四防陷阱（凭据进上下文的六个出口）在企业形态多一条：**数据外发 = 数据安全事件**——一人红队泄的是客户的凭据，企业形态泄的是本企业的客户数据与商业策略，责任主体是你。

| 数据类别 | 能否进外部 AI prompt | 处理方式 |
|---|---|---|
| 客户个人信息（手机号/地址/订单/证件/卡号） | **否** | 测试用自产假数据；真实样本先假名化 |
| 卡数据（PAN/CVV/磁道） | **否，任何形态** | 永不——证据本身都不该有明文 |
| 商业策略数据（成本价/促销预算/供应商合同价） | **否** | 只谈结构与字段名，不谈数值 |
| 内部系统名/域名/接口路径 | 谨慎 | 假名化映射后进 prompt（`system-a`/`api-a.example`） |
| 报错与日志样本 | 脱敏后 | 过脱敏过滤器（去 token/手机号/内部域名）再喂 |
| 场景库结构、脚本生成、报告润色 | **可** | 用假名样本；优先内部批准的 AI 网关 |

**假名化映射管理**：`pseudonym.jsonl`（假名 ↔ 真名映射）放 `secrets/`，权限 0600，**永不进 prompt、不进交付物**。允许用法清单要发给团队：场景库结构化分析、测试脚本生成、三方报文 diff、报告语言润色（假名样本）——边界清楚，工具才用得久。

### 6.1 生态型交战目录模板（多系统关联）

# system-map.md（示例片段，全部虚构）
## 业务动作：会员下单（App 端）

`inventory/systems.yaml` 字段契约：`system`（名）/ `domain`（域名）/ `layer`（四层之一）/ `owner`（团队）/ `scope_status`（authorized / pending / external）/ `data_class`（数据级别，接第三章分级）。字段值全部可机器判定——它同时是 scope_check 的数据源（VOL-09C ⑧）与覆盖台账的行索引。

### 6.2 零售场景库作为未来 skill 的 checks 数据源

场景库到自动化 check 的转化路径（成熟度三级：L1 手工用例 → L2 脚本化 → L3 平台 check 跟版触发）：

| 场景库段 | check 化对应 | 说明 |
|---|---|---|
| 场景编号 | check id | `R-TX-01` 直接作为稳定标识 |
| 【测试方法】 | probe 步骤序列 | 参数化（目标/账号/幂等键） |
| 【验证】 | assertion（正向：预期篡改生效的判据；反向：预期 4xx 的判据） | 双向断言，防假阴/假阳 |
| 【陷阱】 | guardrail | 环境开关（生产只跑无害断言）、并发上限、风控感知 |
| 【修复】 | remediation 模板 | 工单自动带修复建议 |
| 【AI 位】 | 辅助生成任务的提示模板 | 脚本生成/diff 类任务的喂养模板 |

check 草案示例（虚构、YAML 示意）：

```yaml
id: R-TX-01-price-tamper
source: VOL-11/R-TX-01
target: "order create endpoint of {{system}}"
probe:
  - step: "拦截下单请求，篡改 totalAmount=0.01（一次一个字段）"
  - step: "对照篡改 freightFee / discountAmount 子项"
assertions:
  positive: "订单创建成功且支付流水=篡改值 → FAIL（存在漏洞）"
  negative: "服务端重算并 4xx/回退原价 → PASS"
guardrails:
  prod: "仅允许 negative 断言（无害重放），禁止真实支付"
  rate_limit_per_minute: 6
remediation_ref: "VOL-11 第二章 R-TX-01【修复】"
```

落地次序建议：**对账类先行**（R-RF-04 四线对账、R-PX-04 积分平衡——判据客观、无资损）；篡改类次之（正向断言必须护栏齐全）；并发类最后（R-TX-03 需要专项授权与压测环境）。

### 6.3 覆盖台账在生态目标上的用法

生态形态的 coverage.json 扩展为"**系统 × 场景**"矩阵（VOL-09C ⑨ 负空间思想的生态版）：

| 字段 | 取值 | 驱动什么 |
|---|---|---|
| surface | `{system} × {场景编号}`（18 × N 格） | 覆盖度的最小单元 |
| 状态 | 已测（带结论）/ 不适用（带理由）/ 待授权 / 未覆盖 | 四态与 VOL-10 复测四态区分开——这是**覆盖**四态 |
| 结论 | 通过 / 发现（链工单号） | 报告"覆盖度与局限性"章节（VOL-07-08 B1） |

三个用法：①**负空间驱动 scope**——"未覆盖"密度最高的系统就是下一轮 scope 申请与场景补测的依据；②**待授权 = 影子资产的机器可读形态**——`inventory/shadow.md` 里每条资产在矩阵里都有对应"待授权"格，授权落地即转"已测"；③**报告自动渲染**——覆盖度章节直接出矩阵截图 + 负空间声明（"以下场景×系统组合在本轮未覆盖，原因如下"），这是生态形态报告里审计员最看重的一页。

## 附录 A 业务逻辑漏洞速查表（五链全量）

用法：交战时把本表当"过账清单"——左列对信号（看到什么就该想起哪个场景），右列是第一发测试请求的构造。一句话测法只是**入口动作**，完整判据回第二章对应场景。表格与 2.6 矩阵同源，字段按"信号驱动"重排。

| 编号 | 场景 | 触发信号（看到什么想起它） | 一句话测法 |
|---|---|---|---|
| R-TX-01 | 价格篡改 | 下行报文里出现金额字段随请求上行 | 下单请求只改 `totalAmount=0.01`，看订单与流水是否跟随 |
| R-TX-02 | 数量负数/小数 | 有多个数量入口（主链/加购/合并支付） | 标品接口提交 `quantity=0.5` 与 `-1` 各一次 |
| R-TX-03 | 并发超卖 | 库存校验与下单分离、或"查库存"在前端 | 库存=1 的 SKU 并发 20 个下单请求，对账成功单数 |
| R-TX-04 | 订单状态机绕过 | 抓包见到 status/orderState 可提交 | 待支付单直接传"发货"状态值，看是否接受跳态 |
| R-PX-01 | 券四断点 | 券生命周期跨领/核销/转赠多接口 | 同 token 重放领券三次；转赠后双账号先后核销 |
| R-PX-02 | 满减顺序与分摊 | 促销叠加规则多、下单退款两端各有金额 | 组合单退一件，验证"退款+剩余实付==原实付" |
| R-PX-03 | 秒杀资格与库存 | 秒杀页有资格 token/sign 字段 | 持资格连下限购+2 单；秒杀品走普通结算路径 |
| R-PX-04 | 积分汇率与转移 | 抵扣接口带积分数/汇率字段 | 改 `payPoints` 超持有量；双号并发对转同笔积分 |
| R-RF-01 | 退款金额篡改 | 退款请求回传金额；有余额退款路径 | 改 `refundAmount=实付×2`，换余额路径再试 |
| R-RF-02 | 部分退款累计超限 | 支持多次部分退款 | 同单连退 60/60/60（实付 100），记累计边界 |
| R-RF-03 | 退款不退货 | 存在"仅退款"选项与自动退款阈值 | 已签收单申请仅退款（未收货理由），看凭证门槛 |
| R-RF-04 | 库存资金双线不一致 | 退款是跨服务编排（订单+库存+支付） | 全链四元组快照对账（状态/库存/资金/积分） |
| R-MB-01 | 会员等级越权 | 响应含 level/grade，权益按等级门控 | V0 账号请求带 V6 标识调专属价/专属券接口 |
| R-MB-02 | 权益冒领 | 权益领取接口带 targetMemberId | 重放新人礼三次；双测试账号互为目标领取 |
| R-MB-03 | 注销残留 | 有注销入口 | 注销后同手机号重注册，比对可见数据；旧 token 重放 |
| R-SC-01 | 供应商门户横向越权 | 门户接口带 supplierId/vendorId 参数 | A 会话带 B 的 supplierId 请求对账单，一张截图即止 |
| R-SC-02 | 采购审批绕过 | 审批流接口按 nodeId/approver 推进 | 申请人直接调 approve 接口推进自建草稿单 |

## 附录 B 常见零售系统技术栈指纹（公开知识层面）

**声明**：本附录只覆盖**公开通用的开源组件与平台类别**（组件名均为公开开源项目或行业通称），用途是缩小测试面与准备利用面；**不构成对任何企业内部架构的推断依据**——指纹指向"这类组件的公开已知行为"，仅此而已。组件的具体版本号确认后，去公开漏洞库（CVE/NVD 类）核对，本附录不罗列具体漏洞编号。

### B.1 分层指纹表

| 层 | 常见公开组件类别 | 指纹识别要点 | 测试准备动作 |
|---|---|---|---|
| 前台 App | 原生 Android/iOS；跨端框架（React Native/Flutter/Taro/uni-app 类） | APK 内 so 库与资源结构、JS bundle 特征、H5 容器标识（VOL-05 客户端分析） | 拿到包结构→定抓包与逆向路径 |
| 小程序 | 公开小程序平台的标准框架 | 开发者工具可本地调试、包结构与公开规范一致 | 优先开代理调试而非抓 HTTPS |
| Web 商城 | 前端框架（Vue/React 系）+ BFF | JS bundle 结构、路由模式、接口前缀 | 从 JS 提取接口清单（VOL-01 攻击面建立） |
| 接入层 | Nginx；API 网关（Kong/APISIX 等开源系）；CDN/WAF | 响应头（Server、网关自有头）、统一错误结构、429/503 限流响应形态 | 先分层：网关拦截 ≠ 业务校验（第一章 1.2 ②） |
| 后端服务 | Spring Boot/Spring Cloud、Dubbo、.NET（POS 后端常见）、Node.js BFF | Whitelabel 错误页、/actuator 类端点、报文风格、token 结构（JWT/自研） | 公开组件=公开已知行为面；按 VOL-01 未授权探测清单过一遍 |
| 消息/中间件 | Kafka/RocketMQ/RabbitMQ、Redis、MySQL/PostgreSQL | 异步任务回执形态、幂等键设计、延迟消息特征 | 竞态类场景（R-TX-03）先看幂等键是否存在 |
| POS/门店 | Windows/.NET 或 Android 收银机、电子价签（ESL）私有协议、门店 IoT | 门店内网环境、私有协议、固件形态 | 专项授权形态（第一章 1.2 陷阱④），常规模板不适用 |
| 边缘集成 | 持牌支付渠道 SDK、物流/短信开放 API | 回调报文格式、验签方式（渠道公开文档） | 回调伪造只在渠道沙箱（R-TX-04） |

### B.2 指纹→动作映射的三条纪律

1. **指纹只缩小面，不定性**："响应头像 Kong"只说明接入层用了这类网关，不代表后端组件可推断——下一步是用公开文档核对该组件的默认行为（限流响应、路由语法），不是脑补架构。
2. **公开组件的默认配置是第一测试点**：开源组件的默认管理端点、默认错误页、默认路由约定都是公开文档写明的——默认配置未收紧是内部系统最常见的"低垂果实"（VOL-02 1.3 的 Actuator 清单在此复用）。
3. **版本确认走公开漏洞库，结论留在"存在已知公开漏洞组件"层面**：具体 CVE 的可利用性判断要实验验证，报告写"组件+版本+公开漏洞库存在记录+已验证/未验证"，不写"必然可利用"。

### B.3 指纹采集的最小动作清单

| 动作 | 目的 | 红线 |
|---|---|---|
| 响应头 / 错误页 / 路由约定与公开文档核对 | 分层判断（网关 / 框架 / 业务自研） | 只读请求，不碰管理端点写操作 |
| 前端 JS 接口清单提取（VOL-01 攻击面建立） | 拿到全量入口与旧版本路由 | 纯静态分析，可零请求完成 |
| APK / 小程序包结构分析（VOL-05） | 客户端入口、固化旧接口、硬编码常量 | 仅限授权包体 |
| 管理端点探测（VOL-02 1.3 清单） | 默认配置未收紧排查 | 探测频率限额，避开业务高峰 |

指纹动作本身也要过 scope 与护栏——"我只是识别组件"不豁免"对未授权资产发请求"的红线（第一章 1.2 陷阱③）。

## 结语：入职 90 天的地形换装路线

| 阶段 | 动作 | 本卷对应 |
