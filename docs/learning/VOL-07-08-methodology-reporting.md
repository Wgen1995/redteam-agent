# PART A 方法论与成长模型

> 🧭 **导读**：带着 5 年审计功力进场，这一卷先换的不是工具，是“真相从哪来”——像当年从通读代码切到追污点链，这次是从源码切到响应。先摊开全景地图，再改你自己的默认设置，最后上一架按验收计的阶梯：思维旅程，从 A1 起步。

## A1 渗透测试思维全景

### A1.1 四大框架：是什么与何时用

| 框架 | 是什么 | 何时用 |
|---|---|---|
| Kill Chain（网络杀链，Lockheed Martin 七阶段：侦察→武器化→交付→利用→安装→命令与控制 C2→目标行动） | 攻击者视角的攻击链叙事模型 | 报告"攻击路径"章节：把打点→立足→横移→落地写成故事线 |
| PTES（Penetration Testing Execution Standard，渗透测试执行标准；七阶段：前期交互→情报收集→威胁建模→漏洞分析→渗透利用→后渗透→报告） | 管项目全流程的方法论 | 立项与范围（Scope）谈判、交付物定义；一人红队的项目骨架 |
| OWASP WSTG（Web Security Testing Guide，Web 安全测试指南，稳定版 v4.2） | Web 测试用例库，按信息收集、配置与部署管理、身份认证、授权、会话管理、输入校验、错误处理、加密、业务逻辑、客户端等大类组织数十个用例 | Web 系统性覆盖度兜底："该测的都测了"；也是报告"测试方法"章节的引用来源 |
| MITRE ATT&CK（Adversarial Tactics, Techniques and Common Knowledge，对抗战术/技术/常识知识库） | 真实攻击组织 TTP（战术/技术/过程）知识库，企业版矩阵按战术列技术 | 内网行为对照：把内网每个动作映射到技术编号，度量红队覆盖面与蓝队检测盲区 |

选型口诀：**项目管流程用 PTES，Web 覆盖度用 WSTG，内网阶段用 ATT&CK 自查，报告叙事用 Kill Chain**。四者不互斥，完整交付里都会出现。

### A1.2 黑盒信息渐进决策模型（Caldera facts 的通俗版）

【原理】黑盒卡住的实质是**事实缺口**：不知道某类信息，所以不知道下一步做什么。MITRE Caldera（MITRE 官方对手仿真框架）的核心机制之一是事实（facts）：收集到的结构化键值（如主机名、用户列表）；每个能力（ability）声明自己依赖哪些 fact 占位符，引擎用已有 facts 匹配当前可执行的能力——"有什么事实，决定能做什么"（机制细节以官方文档为准：<https://caldera.mitre.org/>）。人工版照抄这个思想：维护 facts 表（列：事实/值/来源/时间），每个缺口对应一类收集动作，动作产出新事实，直到事实组合满足某条利用路径的前置条件。

【操作】
1. 建表（Markdown 或 CSV 均可）：`| 事实 | 值 | 来源 | 时间 |`。
2. 按缺口选动作（示例命令可直接复制）：
   - 不知道资产面（子域）：`subfinder -d example.com`（参数以官方文档为准：<https://github.com/projectdiscovery/subfinder>）
   - 不知道端口与服务：`nmap -sV -sC -p- <目标IP> -oA evidence/nmap_full`（`-sV` 服务版本、`-sC` 默认脚本、`-p-` 全端口、`-oA` 三格式输出存证）
   - 不知道 Web 指纹：`whatweb http://<目标>`
   - 不知道目录结构：`ffuf -w /opt/SecLists/Discovery/Web-Content/common.txt -u http://<目标>/FUZZ -mc 200,301,302,403`（<https://github.com/ffuf/ffuf>）
   - 拿到一个有效凭据：先枚举它能碰的资产再评估提权——凭据是事实，不是终点
3. 每完成一步立即把**结论**写入 facts 表（写结论，不贴原始输出）。

【验证】任一时刻你说得清"下一步动作由表中哪条缺口驱动"；说不清的动作不做。当某条利用路径的前置条件（如：可达端口＋存在组件＋可用凭据）全部闭合时，能明确写出"已满足"。

【陷阱】①上来全端口轰炸：慢、吵、触发防护，应小步快跑；②收集不落表，碰到同目标全部重来；③把"扫完了"当"收集完了"——原始输出不是事实，提炼出的结论才是。

【练习】①本地起 OWASP Juice Shop（`docker run --rm -p 3000:3000 bkimminich/juice-shop`，<https://owasp.org/www-project-juice-shop/>），做 30 分钟纯信息收集，产出 ≥20 行 facts 表；②对照 WSTG"信息收集"章节（<https://owasp.org/www-project-web-security-testing-guide/>）逐项检查补漏。

## A2 审计员→渗透者思维转换表

> 🧭 **导读**：A1 是往外看——地图与决策；这一节往内看，动的是你 5 年养成的默认设置。审计直觉在这里一半是资产、一半是负债，这张表就是分拣清单；换完脑子，A3 的阶梯才踩得实。

| 维度 | 源码审计（旧我） | 渗透测试（新我） |
|---|---|---|
| 真相来源 | 代码即真相 | 响应即真相 ＋ 证据链 |
| 完备性 | 覆盖所有调用点与污点汇聚点（sink） | 覆盖率让位于"路径打通"：打通一条链比列十条可疑更有价值 |
| 边界单位 | 函数/模块/数据流 | 资产/信任边界/网络分区 |
| 验证方式 | 写 PoC 代码、读单测 | 可复现 POC 卡片 ＋ 成对请求响应留档 |
| 影响评估 | 漏洞原理层面 | 打通后的影响放大：提权、横向移动、核心数据 |
| 时间模型 | 基本不受限 | 授权窗口（测试时间窗）硬约束，动作要排优先级 |

### "响应即真相"工作流

【原理】黑盒下唯一可信的输入是服务端返回：状态码、响应头/体、时序、带外（Out-of-Band）回连。证据链＝请求响应成对留存＋时间戳＋判定标准，任何结论可被第三人回放。

【操作】①全流量过代理：浏览器挂 Burp Suite Proxy，测试期间禁止直连；②每个测试点先发一次基线（Baseline）请求再发 payload，两条都留档；③判定信号写进用例：回显差异（响应体/长度变化）、时延差异（与基线对比）、带外信号（DNSLog/自建监听）；④结论一律引用 Burp History 条目号或导出文件名。

【验证】任取一条结论，在 Burp Repeater 重放所引请求，应得到与记录一致的响应；做不到的降级为"疑似"，不得写入报告。

【陷阱】①只看页面渲染不看原始响应，漏掉注释、隐藏字段、状态码差异；②在浏览器 DevTools 里改参数导致代理没记录，证据链断裂；③截图只截"结果"不截"请求"。

【练习】在 vulhub 的 thinkphp/5-rce（ThinkPHP 5.x 远程代码执行 RCE，<https://github.com/vulhub/vulhub>）上各打一次：审计视角（先看官方修复 diff 再构造 payload）与黑盒视角（仅凭指纹与报错特征探测），记录两条路径的 facts 消耗差异。

## A3 能力阶梯 L0–L5（能力里程碑制，不设时间）

> 🧭 **导读**：脑子换好了（A2），从这里转入人生旅程：这架阶梯不按学时计、按验收定级，每一级都是能被第三人检验的动作，而不是“我看过了”。节奏提醒——先诚实定级再谈爬升，跳级攒下的手感会在真实项目里露馅。

进度单位是"里程碑验收通过"，不是学时。每级四件套：能力清单/验收标准/推荐靶场材料/自测清单。

**L0 环境与工具就绪**
- 能力清单：Kali 虚拟机、Docker、Burp Suite、nmap、ffuf、sqlmap、nuclei、字典库 SecLists 就位；虚拟机快照与工具版本记录习惯。
- 验收标准：从空机器 30 分钟内重建可用测试环境；每个工具能说出 3 个常用参数的含义。
- 材料：Kali 官方文档、SecLists（<https://github.com/danielmiessler/SecLists>）。
- 自测：□Burp 证书装入 Firefox □vulhub 可起停 □快照已建 □工具版本表已填。

**L1 靶场可复现已知漏洞**
- 能力清单：只看官方 advisory（不看 writeup）复现单个 CVE，能解释 payload 每一段；产出合格 POC 卡片（见 B2）。
- 验收标准：随机抽一台 vulhub 靶机，独立复现成功且卡片能被第三人复现。
- 推荐：log4j/CVE-2021-44228（Log4j2 JNDI 远程代码执行）、bash/CVE-2014-6271（Shellshock）。
- 自测：□能解释 payload 每段 □能写出 CVSS 向量（见 B3）□复现后 `docker compose down -v` 清理。

**L2 独立完成 vulhub 全类**
- 能力清单：按类别打穿：反序列化（Deserialization：shiro/CVE-2016-4437、fastjson/1.2.24-rce）、框架 RCE（struts2/s2-045、thinkphp/5-rce、confluence/CVE-2022-26134）、中间件（weblogic/CVE-2020-14882、tomcat/CVE-2017-12615、jenkins/CVE-2018-1000861）、未授权访问（Unauthorized Access：redis/4-unacc、elasticsearch/CVE-2015-1427）、认证缺陷（mysql/CVE-2012-2122）。
- 验收标准：每类抽签复现 ≥1 台；同原理换组件时不查文档能自行构造利用思路。
- 自测：□每台一张 POC 卡片 □能写出每类漏洞利用链的前置条件（facts 视角）。

**L3 HTB easy→medium 独立通关**
- 能力清单：完整盒子流程：枚举→打点→user flag→本机提权→root flag；Linux/Windows 各 ≥3 台；Windows 侧掌握 SMB、WinRM、活动目录（Active Directory, AD）基础。
- 验收标准：easy 机 3 小时内独立双 flag；medium 机独立通关并写一页复盘（入口/提权/走过的错路）。示例：easy Linux——Lame、Shocker、Nibbles；easy Windows——Sauna、Active、Grandpa；medium——Resolute、Cascade、Monteverde（Windows AD）、Cronos、DevOops（Linux）。退役机需 HTB VIP 订阅访问，难度以官方页面为准（<https://www.hackthebox.com>）。
- 材料：HTB Academy 模块、IppSec 复盘视频（<https://ippsec.rocks>）。
- 自测：□每台一页复盘 □能用 ATT&CK 编号映射自己用到的技术（<https://attack.mitre.org>）。

> 🧭 **导读**：到这里你应该有的手感：一台陌生靶机从枚举到双 flag 一条龙不打怵，每步动作都能对上 ATT&CK 编号。L4 起规则变了——flag 换成证据，“打通”换成“零返工”，PART B 从此不是参考资料，是验收标准。

**L4 真实授权项目辅助位**
- 能力清单：在资深人员主导下负责子模块（外部打点、Web 漏洞挖掘），按规范交付证据与报告初稿。
- 验收标准：所负责子模块零返工：POC 全部可复现、评级偏差 ≤1 级（见 B3）、证据合规（见 B4）。
- 材料：本卷 PART B 全部 ＋ 甲方/公司报告模板。
- 自测：□卡片交接测试通过 □报告章节无结构性返工。

**L5 一人红队独立交付**
- 能力清单：独立跑完授权项目全流程：范围谈判→测试→报告→复测（见 B6）；AD 内网攻击在 GOAD 实验室落地（<https://orange-cyberdefense.github.io/GOAD/>，含 Kerberoasting、AS-REP 烘焙、口令喷洒等大量故意留置漏洞，完整清单以官方文档为准）——完整版 GOAD（5 VM/2 森林/3 域），资源紧张用 GOAD-Light。
- 验收标准：独立交付一份客户签字接受的完整报告＋复测报告，全程零出授权范围。
- 自测：□报告一次过内部评审 □复测闭环 □项目归档完整。

### L1 标准复现动作（以 vulhub 为例）

【原理】靶场复现的价值在动作标准化：环境→验证→利用→留证→清理，形成肌肉记忆后原样迁移到真实项目。

【操作】
```bash
cd vulhub/log4j/CVE-2021-44228
docker compose up -d
docker compose ps                 # 确认状态与端口映射
curl -I http://127.0.0.1:8080     # 确认可达（端口以 ps 输出为准）
# 按 advisory 构造 payload（JNDI 回连），在 DNSLog/监听端确认命中并截图留证
docker compose down -v            # 清理
```
【验证】`docker compose ps` 显示 running；监听端收到回连即利用成功；POC 卡片交第三人 10 分钟内复现。

【陷阱】①端口占用导致 compose 起不来（先清理再重试）；②payload 打错 JNDI 协议前缀（ldap/rmi 区分）；③复现完不清理，多靶机残留互相干扰。

【练习】为自己定级（L0–L5），对下一级写逐项差距清单，挑差距最小的一项本周期补齐。

# PART B 报告与交付

> 🧭 **导读**：测试做完≠交付完成——客户签字的对象是报告，不是你的 payload。PART B 进入交付旅程：你写审计报告的底子直接复用，新加的硬规矩只有一条——每个结论都要能被第三人原样重放，做不到的进不了报告。

## B1 中文渗透测试报告标准结构

【原理】报告是唯一交付物，客户"修不修、先修谁"只依赖它；结构固定则评审可对照检查单、模板可复用、避免漏项。

【操作】六节结构，逐节写法：
1. **概述**：项目背景；授权依据（合同/授权书编号、测试时间窗、测试方与联系方式）；总体结论一段话：高危 X/中危 Y/低危 Z、整体风险判断、最严重的 1–2 条攻击链；结论先行，管理层不读细节也能懂。
2. **测试范围与方法**：资产清单表（域名/IP/应用/账号类型）；方法论引用（PTES 阶段划分＋WSTG 章节对照）；工具及版本表；测试限制（未覆盖项与原因：物理、社会工程学、拒绝服务 DoS 等未做）。写法：这是范围争议的防火墙——没写进范围的等于没测。
3. **风险矩阵（Risk Matrix）**：严重度×漏洞类型二维矩阵，只放数量分布；附评分标准：CVSS 3.1 分档——严重（9.0–10.0）/高（7.0–8.9）/中（4.0–6.9）/低（0.1–3.9）。
4. **漏洞明细**：每个漏洞一张 POC 卡片（见 B2），按严重度降序排列。
5. **修复建议汇总**：总表：漏洞ID/严重度/修复建议/优先级（P0 立即–P3 排期）/建议责任方（应用/运维/网络）；与明细逐条对应，不出现明细里没有的条目。
6. **复测说明**：复测范围、时间安排、四态判定口径（见 B6）与结果模板。

【验证】交叉三查：概述里的数字＝矩阵合计＝明细条数；每个漏洞在第 5 节有对应建议行；第 3 人只拿报告能复现任一漏洞。

【陷阱】①把工具原始输出贴进正文（应放附录并引用）；②范围写"部分系统"这类模糊表述；③结论写"系统安全/不安全"的二元判断——报告只陈述风险与成立条件。

【练习】把 A2/A3 产出的 3 个漏洞组装成六节迷你报告（模板可直接复用）。

## B2 POC 卡片规范＝可复现标准

【原理】POC 卡片（Proof of Concept card）是漏洞明细的最小单元，合格标准只有一条：拿到卡片的工程师**不咨询你**、10 分钟内复现并确认。

【操作】卡片字段与写法：
- **编号与标题**：`VULN-001｜越权访问（Broken Access Control）｜高危`
- **环境假设**：目标 URL、所需账号及获取方式（如"userA：普通用户，前台可注册"）、测试时间窗。缺了它复现第一步就卡死。
- **复现步骤**：编号到每一步，一步一个动作。
- **完整请求**：方法＋路径＋全部关键头＋体，能直接粘进 Burp Repeater，同时给 curl 形式。
- **预期响应**：状态码＋关键响应行，写明"看到什么算成功"。
- **截图**：全屏含 URL 栏与系统时间、高亮关键行、已脱敏（见 B4）、每个漏洞 2–4 张。
- **影响与评级**：一句话影响＋CVSS 向量串（见 B3）。

示例（水平越权）：
```http
GET /api/orders/1001 HTTP/1.1
Host: target:8080
Authorization: Bearer <userA的token>
```
预期响应：`200`，返回 owner＝userB 的订单——普通用户 A 无需交互即可读任意用户订单。curl 等价：`curl -H "Authorization: Bearer <userA的token>" http://target:8080/api/orders/1001`。

【验证】交接测试：找一个没接触过该系统的同事照卡片复现，失败即不合格，改到通过为止——这是卡片能否进报告的唯一标准。

【陷阱】①缺环境假设（账号哪来的没写）；②请求缺关键头，复现直接 401；③只写"越权了"不写预期响应指纹；④截图无时间无 URL，事后无法对应。

【练习】为 vulhub 的 shiro/CVE-2016-4437（Shiro rememberMe 反序列化）写完整卡片：含 rememberMe Cookie 的完整请求、判定标准（如 DNSLog 回连）、脱敏截图。

## B3 CVSS 3.1 评级实操

【原理】CVSS 3.1（Common Vulnerability Scoring System，通用漏洞评分系统）基本分由 8 个指标构成向量串（Vector String）：攻击向量 AV/攻击复杂度 AC/所需权限 PR/用户交互 UI/作用范围 S（Scope），加上机密性 C/完整性 I/可用性 A 三维影响，组合映射 0–10 分；分档见 B1 第 3 节。

【操作】定级流程：①先定影响——能读什么（C）、能改什么（I）、能停什么（A），各取 H/L/N；②再定可达性——AV:N 网络可达？AC:L 稳定复现无特殊条件？PR:N 完全无需权限？UI:N 无需受害者配合？；③Scope 只有当漏洞影响**超出**被授权组件边界（应用权限→宿主机、波及其他租户）才取 S:C。模板示例：
- 未授权 RCE：`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`（9.8，严重）
- 需低权限登录的水平越权读数据：`CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`（6.5，中）
- 反射型 XSS（Cross-Site Scripting）：`CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:U/C:L/I:L/A:N`（6.1，中）

【验证】在 FIRST 官方计算器复算，分数与严重档一致：<https://www.first.org/cvss/calculator/3.1>。双人独立评级，差 >1 级时逐指标对照向量找分歧点。

【陷阱】常见误评级：①S:C 滥用——"理论上可能影响别的系统"不等于已越信任边界；②"注册个账号就能打"是 PR:L 不是 PR:N；③越权一律评低——能读订单/身份等核心数据应 C:H；④仅内网可达的漏洞 AV 应取 A（邻接 Adjacent），分数显著下降；⑤默认弱口令评低——按"凭据即全部权限被夺"评估实际影响，而不是按"口令问题"。

【练习】给 B1 迷你报告的 3 个漏洞独立定级，与同伴互换向量逐项比对分歧。

## B4 证据留存与脱敏

【原理】证据链服务三方：客户复现、内部评审、争议仲裁。脱敏的最小化原则：报告只保留证明漏洞存在所必需的数据，多一个字段都是风险。

【操作】留存目录与命名：
```
evidence/
  VULN-001/
    step2_request.txt      # Burp 导出的成对请求响应
    step2_response.png
    SHA256SUMS
```
关键原始文件算哈希留档：`shasum -a 256 evidence/VULN-001/* > evidence/VULN-001/SHA256SUMS`。脱敏规则：①凭据（密码/token/私钥）一律不进报告与截图，用 `<已脱敏>` 占位，原件单独加密交付指定收件人；②个人敏感信息打码（手机号保留前 3 后 4）；③数据泄露类证明取样例：前 5 条记录＋总行数（如 `SELECT COUNT(*)`），**禁止**整表拖库进附件；④交付包加密压缩，密码走另一信道（电话/短信）发送。

【验证】交付前全文检索密码字段、`Bearer`、token、手机号/身份证正则无命中；抽查截图边缘无敏感信息。

【陷阱】①POC 步骤里写明文口令（哈希也别写）；②截图顺手带出他人手机号/内网拓扑；③把整表数据当"强证据"塞附件——违规且撑爆邮箱。

【练习】对 B2 的卡片跑一遍脱敏自检表，两人互查。

## B5 等保语境下的渗透测试报告要点

【原理】等级保护（等保 2.0）体系下，三级及以上系统按 GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》建设整改，等级测评依据 GB/T 28448-2019《测评要求》与 GB/T 28449-2018《测评过程指南》执行；渗透测试常作为测评之外的补充验证或整改复核，报告要能"翻译"到等保语言。

【操作】在 B1 结构上增加：①关联定级对象与备案信息（范围与备案边界一致）；②漏洞-条款映射表：每个漏洞对应基本要求的安全条款大类（身份鉴别、访问控制、入侵防范、数据保密性/完整性等），并写出整改后应满足的要求表述；③风险等级在 CVSS 之外补充"高/中/低"表述，衔接测评报告的问题等级；④复测结论纳入整改闭环（见 B6）。条款号务必对照最新官方文本填写（全国标准信息公共服务平台可查原文），不凭记忆写。

【验证】映射表逐行可追溯到基本要求原文表述；全文不出现"测评通过/不通过"——那是测评机构的结论，渗透报告只陈述风险。

【陷阱】①把渗透报告写成测评报告（越界做符合性判断）；②凭记忆写条款号被评审打回；③授权范围与备案系统边界不一致导致报告无法被引用。

【练习】取 GB/T 22239-2019 公开文本，把迷你报告 3 个漏洞映射到安全条款大类（先练大类，不写具体条号）。

## B6 复测与回归验证流程

【原理】复测（Retest）验证整改有效性，向后看旧漏洞；回归（Regression）确认修复没引入新问题，向前看改动面。二者分开执行、都留证据。

【操作】六步流程：
1. 复测授权确认：沿用初始范围与时间窗，超出部分重新授权。
2. 逐漏洞按原 POC 卡片**原样重放**，记录新响应。
3. 修复方式核验：区分"根因修复"（代码/配置已改）与"缓解"（WAF 拦截、封 IP）——后者在报告中标注"缓解，未根因修复"。
4. 回归：对修复点周边重测（同端点同类参数、同框架其他路由），加快扫兜底：`nuclei -u https://<目标> -severity critical,high`（参数以官方文档为准：<https://github.com/projectdiscovery/nuclei>）。
5. 复测报告：每个漏洞标四态——已修复/部分修复/未修复/风险接受（风险接受必须有客户书面确认）；新发现单独列出。
6. 归档：初始报告、复测报告、证据包关联存档。

【验证】四态判定每条都有重放响应截图支撑；回归有清单（测了哪些相邻面）。

【陷阱】①"不弹了"就判修复——可能是 WAF 拦截或网络策略变化，换编码/路径/网络位置再验证；②只测原端点不测同类端点；③复测窗口没重新拿授权；④风险接受无书面记录，事后争议说不清。

【练习】在 vulhub 的 mysql/CVE-2012-2122（MariaDB 认证绕过）上模拟全流程：出卡片→实施"修复"（限制访问来源或更换镜像）→按六步走完并产出复测报告。
