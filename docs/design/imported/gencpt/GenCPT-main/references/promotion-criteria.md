# 攻击模式晋升标准

本文档定义攻击模式库中学习模式的晋升门槛、晋升流程、来源标记和降级归档规则。

---

## 1. 晋升门槛

一个 LLM 推理发现要晋升为攻击模式库中的正式模式，必须 **4 项全满足**：

### 门槛 ①：差分证明充分

**定义**：攻击前后状态对比明确，至少包含 2 个可观测差异。

**判定标准**：
- 攻击前状态有明确的观测数据（如 L0 命令输出、L1 容器内观察结果）
- 攻击后状态有明确的变化证据（如新进程、新文件、权限变化、网络连接）
- 前后对比至少有 2 个独立的可观测差异点（不能只依赖单一证据）
- 差分证明不依赖攻击者自身行为的变化（如"我执行了命令"不算差分）

**示例**：
- 攻击前：容器内无法读取宿主机文件 + docker ps 无异常容器
- 攻击后：容器内可读取宿主机 `/etc/shadow` + docker ps 出现新 alpine 容器
- ✅ 有 2 个独立差异点 → 差分证明充分

**反例**：
- 攻击前：未执行过 `cat /etc/shadow`
- 攻击后：执行 `cat /etc/shadow` 返回内容
- ❌ 只有一个差异点（命令输出本身），且依赖于攻击者行为 → 差分证明不充分

### 门槛 ②：探测可复现

**定义**：SSH 执行探测命令清晰，同类型环境可执行。

**判定标准**：
- 探测命令全部为实际可执行的 SSH 命令（不含占位符、不含理论推导步骤）
- 探测命令标注了执行上下文层级（L0/L1/L2/L3）
- 同类型环境（相同平台、类似配置）可复现相同探测结果
- 探测命令不依赖特定环境的一次性状态（如临时文件、随机端口）
- L3（条件验证）的推导逻辑清晰且基于可观测的条件组合

**示例**：
- 探测命令：`[L1] kubectl exec xxx -- ls -la /var/run/docker.sock` → 明确可执行 ✅
- 推导逻辑：`特权容器 + 无资源限制 = 可 fork bomb` → 条件可观测 ✅

**反例**：
- "理论上可以通过 X 方式逃逸" → 无实际命令 ❌
- "根据 CVE-XXXX 可能受影响" → 未验证当前环境 ❌

### 门槛 ③：无法匹配现有模式

**定义**：不是已有攻击模式的变体。

**判定标准**：
- 与现有攻击模式库（`attack-patterns/` 所有 SKILL.md）逐一比对
- 以下情况视为"变体"，不可晋升为新模式：
  - 相同攻击面，仅前置条件参数不同（如不同版本的同一 CVE）
  - 相同攻击路径，仅目标平台不同（如 docker 和 containerd 的同一逃逸方式）
  - 相同攻击技术，仅绕过策略不同（如不同 AppArmor 规避方式属于同一模式的不同介绍）
- 同一攻击路径的变体应更新现有模式的 `hit_count`，不新增模式

**示例**：
- 发现新的 Docker Socket 逃逸方式 → 已有 `socket-escape` 模式 → 是变体，更新 hit_count ✅
- 发现 containerd-shim 逃逸（AS-1 中无此模式）→ 全新模式 → 可晋升 ✅

### 门槛 ④：跨会话命中 ≥2 次

**定义**：在不同环境独立命中，偶然性排除。

**判定标准**：
- 至少在 2 个不同的测试会话中独立命中（不同 session_dir）
- 2 次命中的环境指纹不同（如不同 k8s 版本、不同节点数、不同 Pod 配置）
- 同一会话中多次执行同一探测不算多次命中
- 偶然命中（如只在某个极端配置下触发）需额外证据说明可复现性

**示例**：
- 会话 A：在 K8s 1.29 集群中发现 nsproxy 逃逸
- 会话 B：在 K8s 1.27 集群中独立发现 nsproxy 逃逸
- ✅ 跨 2 个会话独立命中 → 满足门槛

**反例**：
- 同一会话中执行 2 次相同探测 → 只算 1 次命中 ❌
- 只在 1 个会话中发现 → 不满足 ❌

## 2. 晋升流程

```
Phase 4b 产出 insights.md（LLM 推理发现）
        ↓
Phase 9 或独立运行 /gencpt-evolve
        ↓
  ┌─── 1. 收集洞察 ───┐
  │  读 insights.md     │
  │  读 session_history.md │
  │  读 _index.md       │
  └────────┬───────────┘
           ↓
  ┌─── 2. 逐条评估 ───┐
  │  a. 与现有模式比对  │
  │     → 变体：更新 hit_count，不新增 │
  │  b. 晋升门槛检查    │
  │     ① 差分证明充分？ │
  │     ② 探测可复现？  │
  │     ③ 无法匹配现有？ │
  │     ④ 跨会话≥2次？  │
  │     → 全满足：标记可晋升  │
  │     → 不满足：记原因，保留在 insights.md │
  └────────┬───────────┘
           ↓
  ┌─── 3. 用户审批 ───┐
  │  question 工具逐条确认 │
  │  → 添加：晋升为新模式  │
  │  → 拒绝：记录原因，不晋升 │
  │  → 暂存：保留在 insights.md，下次再评估 │
  └────────┬───────────┘
           ↓
  ┌─── 4. 生成模式 ───┐
  │  读 promotion-template.md │
  │  生成 8 段结构 SKILL.md   │
  │  写入 attack-patterns/{攻击面}/_learned/{slug}/SKILL.md │
  │  更新 _index.md（hit_count, last_hit） │
  │  更新 attack-hypotheses.md │
  │  更新 _learned_index.md   │
  └────────┬───────────┘
           ↓
  ┌─── 5. 一致性维护 ───┐
  │  LLM 语义检查三库一致性 │
  │  compliance-hypotheses.md │
  │  attack-hypotheses.md    │
  │  cross-ref-queries.md    │
  │  不一致 → 输出不一致项列表 │
  └──────────────────────┘
```

## 3. 来源标记

每种来源有对应的标记和生命周期规则：

| 来源 | 标记 | confidence 初始值 | 初始位置 | 生命周期规则 |
|------|------|-----------------|---------|------------|
| 人工编写 | 📚 `manual` | high | `attack-patterns/{攻击面}/{slug}/SKILL.md` | 永远 high，不降级。只更新 hit_count 和 last_hit |
| 策展审核 | 🎯 `curated` | high | `attack-patterns/{攻击面}/{slug}/SKILL.md` | 永远 high，不降级。只更新 hit_count 和 last_hit |
| LLM 学习 | 🧠 `learned` | medium | `attack-patterns/{攻击面}/_learned/{slug}/SKILL.md` | 见降级规则 |

### 来源在报告中的显示

| 来源标识 | 代码 | 报告中显示 |
|---------|------|-----------|
| pattern_library | 📚 | 已知攻击模式库 ({模式名}) |
| llm_reasoning | 🧠 | LLM 推理分析 (Phase 4b) |
| learned | 🔄 | 学习模式 ({模式名}, promoted {日期}) |

## 4. 降级归档规则

### 4.1 learned 模式置信度升级规则

| 当前 confidence | 升级条件 | 升级后 confidence |
|----------------|---------|-----------------|
| medium | 命中 ≥5 次且跨 ≥2 环境 | high |

### 4.2 learned 模式降级规则

| 当前 confidence | 降级条件 | 降级后 confidence | 操作 |
|----------------|---------|-----------------|------|
| high | 连续 5 次检测未命中 | medium | 继续使用 |
| medium | 连续 10 次检测未命中 | stale | 继续使用但标记 |
| stale | 连续 15 次检测未命中 | — | 询问用户是否归档 |
| 任何 | 确认误报（差分证明错误） | — | 立即归档到 `_archived/` |

### 4.3 归档规则

归档条件：
1. 连续 15 次检测未命中且用户确认归档
2. 确认误报（差分证明逻辑错误）
3. 用户主动标记归档

归档操作：
1. 将 SKILL.md 从 `attack-patterns/{攻击面}/_learned/{slug}/` 移动到 `attack-patterns/{攻击面}/_archived/`
2. 在 `_index.md` 中标记为 `archived`
3. 在 `_learned_index.md` 中标记为 `archived`，记录归档原因和日期
4. `attack-hypotheses.md` 中对应条目标记为 `archived`

### 4.4 降级与归档的时间线

```
learned 模式生命周期：

创建（medium）
    │
    ├─ 命中 ≥5 次跨 ≥2 环境 → 升级为 high
    │                           │
    │                           ├─ 保持 high（继续使用）
    │                           └─ 连续 5 次未命中 → 降级为 medium
    │                                                      │
    │                                                      └─ 连续 10 次未命中 → stale
    │                                                                               │
    │                                                                               └─ 连续 15 次未命中 → 问用户 → 归档
    │
    ├─ 连续 5 次未命中（仍在 medium）→ 保持 medium
    │       │
    │       └─ 连续 10 次未命中 → stale
    │               │
    │               └─ 连续 15 次未命中 → 问用户 → 归档
    │
    └─ 确认误报 → 立即归档

manual/curated 模式：
    │
    └─ 永远 high，只更新 hit_count 和 last_hit，不降级不归档
```

### 4.5 hit_count 更新规则

- 每次检测会话结束时，更新 `attack-patterns/_index.md` 中所有命中模式的 `hit_count` 和 `last_hit`
- `hit_count`：累计命中次数（跨所有会话）
- `last_hit`：最后一次命中的日期（`YYYY-MM-DD` 格式）
- 跨会话 baseline 命中也计入 `hit_count`
- 模式命中但前置条件不满足（证伪）不计入 `hit_count`

### 4.6 准确性指标

准确性低于 70% 的 learned 模式应当标记为需要审查：

| 指标 | 计算 | 阈值 | 处理 |
|------|------|------|------|
| 命中率 | 命中次数 / 总检测次数 | < 10% | 降级（见降级规则） |
| 准确性 | 前置条件满足且攻击成功 / 前置条件满足总数 | < 70% | 标记待审查，下次检测优先验证 |
