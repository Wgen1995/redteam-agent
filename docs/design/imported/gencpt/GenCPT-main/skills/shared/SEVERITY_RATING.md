# SEVERITY_RATING — 漏洞验证程度与可信度分级

## 1. 五级验证程度

| 级别 | 条件 | 报告标注 | 可信度 | 执行上下文 | 全景报告位置 |
|------|------|---------|--------|-----------|-------------|
| 确认漏洞 (confirmed) | 5项门槛全满足（前置条件可复现+可执行+可区分+影响可观测+可恢复） | ✅✅ 已确认-可复现 | C1 实证复现 | 至少L2差分证明 | 漏洞主体 + 覆盖矩阵 |
| 条件成立 (condition_met) | 前置条件满足但被安全机制阻断或差分证明不充分 | ✅ 条件成立（附阻断机制或差分不足原因） | C2 条件实证 | 至少L1前提验证 | 漏洞主体 + 覆盖矩阵 |
| 高风险线索 (high_risk_clue) | 合规违规+攻击映射高风险但前置条件不完全满足 | ⚠️ 高风险线索（附待验证说明） | C3 风险线索 | 至少L0条件发现 | 漏洞主体 + 覆盖矩阵 |
| 不可利用 | 已检查，前置条件不满足 | ➖ 已证伪（附证伪依据） | — 已证伪 | 至少L0证伪依据 | 覆盖矩阵（不可利用行） |
| 已阻断 | 被安全机制阻断 | 🛑 已阻断（附阻断机制名称） | C2 条件实证 | 至少L1阻断证据 | 漏洞主体 + 覆盖矩阵 |

每一条都有完整证据链，不留黑箱。

## 2. C1/C2/C3 可信度定义

### C1 实证复现 ✅✅

实际执行攻击路径，差分证明成功。必须满足：

- **5项确认门槛全满足** + **L2执行上下文差分证明**
- 攻击命令实际执行且成功复现漏洞路径
- 差分证据充分：攻击前状态 vs 攻击后状态可清晰区分
- 攻击后可恢复到原始状态

### 差分证明的 L0 观测强制要求（按攻击类型分级）

| 攻击类型 | 差分证明结构要求 | 不满足时 |
|---------|----------------|---------|
| **AS-1 逃逸** | 必须包含 `[L0]攻击前基线 + [L2]执行 + [L0]攻击后观测` 三段式 | C1 降级为 C2 |
| **AS-2 认证授权** | `[L0]基线 + [L2]执行 + [L0]观测` 或 `[L1]基线 + [L2]执行 + [L1]观测` | 不强制 L0 |
| **AS-3 网络** | `[L1]基线 + [L2]执行 + [L1]观测` | 不强制 L0 |
| **AS-4 数据泄露** | `[L1]基线 + [L2]执行 + [L1]观测` | 不强制 L0 |
| **AS-5 DoS** | 必须包含 `[L0]资源监控基线 + [L2]执行 + [L0]资源监控对比` | C1 降级为 C2 |
| **AS-6 供应链** | `[L0]基线 + [L1]观测` | 不强制 L2 |
| **AS-7 持久化** | 必须包含 `[L0]宿主机文件检查基线 + [L2]执行 + [L0]宿主机文件对比` | C1 降级为 C2 |

**例外**：hostpath-mount 模式的差分证明为 `[L0]检查hostPath配置 + [L1]读取宿主机文件`，无 L2 执行步骤（攻击本身就是读取操作），不适用三段式要求，但必须有 L0 观测确认 hostPath 挂载存在。

**原理**：逃逸攻击的核心证据是"宿主机视角观测到异常"（新容器/新进程/新文件），不是"容器内觉得自己逃逸了"。DoS 攻击的核心证据是"宿主机资源监控异常"。持久化攻击的核心证据是"宿主机文件系统变化"。这些攻击类型如果只从容器内视角自说自话证明，可能产生虚假确认。

### C2 条件实证 ✅

前置条件全部满足，理论链路完整，但因以下原因不可完整复现。包含两种子情况：

1. **安全机制阻断**：前置条件满足但被 AppArmor/Seccomp/网络策略等阻断 → 标注阻断机制名称
2. **不可安全复现**：前置条件满足但实际执行会影响生产（DoS、删根目录等） → 标注原因 + 理论POC（标注⚠️）

必须提供：
- 前置条件全部列举 + 观测证据
- 理论链路清晰（攻击路径可追溯）
- 不可复现原因（阻断机制名称 或 不可安全复现原因）

### C3 风险线索 ⚠️

配置存在安全隐患但前置条件不完全满足。必须提供：
- 配置证据（合规违规 + 攻击映射高风险）
- 风险分析（哪些条件满足、哪些不满足）
- 建议补充验证（如何进一步验证）

## 3. 确认门槛

### 合规确认门槛（3 项）

| # | 门槛 | 必须证明 |
|---|------|---------|
| 1 | 可检测 | SSH 执行检测命令返回了实际违规证据 |
| 2 | 可归属 | 违规可明确归属到具体 Pod/容器/节点/命名空间 |
| 3 | 影响可说明 | 能说明违规的具体安全影响（映射到攻击假设族） |

### 攻击确认门槛（5 项 + 差分证明）

| # | 门槛 | 必须证明 | 差分证据要求 |
|---|------|---------|------------|
| 1 | 前置条件满足 | 攻击所需条件确实存在 | 观测数据 + 合规映射 edges 证明 |
| 2 | 可执行 | 攻击命令可在目标环境执行且未报错 | 攻击命令输出 vs baseline 输出 |
| 3 | 可区分 | 攻击效果可与正常行为区分 | 攻击前状态 vs 攻击后状态 |
| 4 | 影响可观测 | 攻击成功后的副作用可被观测 | 逃逸：可读写宿主机文件 |
| 5 | 可恢复 | 攻击后可恢复到原始状态 | 清理命令执行后恢复确认 |

**C1 达标要求**：合规3项 + 攻击5项 + L2执行上下文差分证明 = 全部满足。

## 4. 执行上下文层级 L0-L3

| 层级 | 名称 | 执行位置 | 用途 | 命令方式 |
|------|------|---------|------|---------|
| L0 | 宿主机观察 | SSH到宿主机 | 发现前置条件、收集配置信息、差分对比 | `ssh_execute` 直接执行 |
| L1 | 容器内观察 | kubectl exec进入目标Pod | 验证攻击者视角可见性（容器内能看见什么） | `kubectl exec <pod> -- <command>` |
| L2 | 容器内攻击验证 | kubectl exec进入目标Pod + 特权操作 | 实际复现漏洞路径 | `kubectl exec <pod> -- <attack_command>` |
| L3 | 条件验证 | 不执行破坏性命令 | 不可安全复现的漏洞（DoS、删根目录等） | 条件组合 + 理论分析 |

### 层级选择规则

| 漏洞类型 | 优先层级 | 说明 |
|---------|---------|------|
| 容器逃逸 | L1→L2 | 先从容器内看条件，再从容器内执行逃逸 |
| 特权容器滥用 | L1→L2 | 同上 |
| 信息泄露 | L0→L1 | 宿主机发现 + 容器内验证可读性 |
| RBAC权限提升 | L0→L1 | kubectl auth can-i + ServiceAccount token验证 |
| DoS类 | L0→L3 | 宿主机发现条件 + 条件验证（不实际触发DoS） |
| 网络横向移动 | L1→L2 | 容器内curl/nc验证网络可达性 |
| Secret泄露 | L0→L1 | 宿主机发现 + 容器内验证可读性 |
| 持久化 | L0→L1→L2 | 宿主机发现 + 容器内验证 + 实际部署验证（需审批） |

### 各层级执行示例

**L0 - 宿主机观察**：
```bash
ssh_execute(server, "kubectl get pods -o jsonpath='{.items[*].spec.securityContext.privileged}'")
ssh_execute(server, "docker inspect xxx | jq '.[0].HostConfig.Privileged'")
```

**L1 - 容器内观察**：
```bash
ssh_execute(server, "kubectl exec -n production backend-api-pod -- cat /proc/1/cgroup")
ssh_execute(server, "kubectl exec -n production backend-api-pod -- ls -la /var/run/docker.sock")
ssh_execute(server, "kubectl exec -n production backend-api-pod -- cat /proc/self/status | grep Cap")
```

**L2 - 容器内攻击验证**：
```bash
ssh_execute(server, "kubectl exec -n production backend-api-pod -- docker run -v /:/host alpine ls /host/etc/shadow")
ssh_execute(server, "kubectl exec -n production backend-api-pod -- docker rm -f <container_id>")
```

**L3 - 条件验证**：
```markdown
验证级别: L3-条件验证
不可安全复现原因: 实际执行会导致宿主机CPU资源耗尽，影响生产环境
前置条件满足证明:
  - ✅ kubectl get pod xxx -o jsonpath='{.spec.securityContext.privileged}' = true
  - ✅ kubectl get pod xxx -o jsonpath='{.spec.containers[0].resources}' = {} (无限制)
理论风险: 特权容器 + 无资源限制 = 可 fork bomb 导致宿主机 DoS
POC步骤（⚠️理论推导，实际执行会导致服务不可用）
```

## 5. 可信度判定流程

```
攻击模式匹配
    │
    ├─ 前置条件检查（L0+L1）
    │   ├─ 不满足 → ➖ 已证伪，附证伪依据（进入全景报告覆盖矩阵"不可利用"行）
    │   ├─ 部分满足 → ⚠️ C3 风险线索
    │   └─ 满足 → 继续
    │
    ├─ 破坏性评估
    │   ├─ 破坏性操作（DoS/删根目录等）→ L3 条件验证 → ✅ C2 条件实证（标注不可安全复现原因）
    │   └─ 非破坏性 → 继续
    │
    ├─ 攻击验证（L2）
    │   ├─ 成功（差分证明充分）→ ✅✅ C1 实证复现
    │   ├─ 被安全机制阻断 → 🛑 C2 条件实证（标注阻断机制）
    │   └─ 失败（差分不充分）→ ✅ C2 条件实证（附差分不足说明）
    │
    └─ 审批门控
        ├─ L3操作（auto）→ 视结果定C1/C2
        ├─ L4操作（manual）→ question工具确认
        └─ L5操作 → 必须确认
```

## 6. 全景报告中的位置

| 验证程度 | 漏洞主体区 | 覆盖矩阵 |
|---------|-----------|---------|
| ✅✅ 已确认-可复现 (confirmed) | ✅ 出现 | ✅ 出现 |
| ✅ 条件成立 (condition_met) | ✅ 出现 | ✅ 出现 |
| ⚠️ 高风险线索 (high_risk_clue) | ✅ 出现 | ✅ 出现 |
| ➖ 已证伪 | ✗ 不出现 | ✅ 出现在"不可利用"行 |
| 🛑 已阻断 | ✅ 出现 | ✅ 出现 |

- **漏洞主体**：confirmed、condition_met、high_risk_clue、已阻断 写入漏洞详细报告
- **覆盖矩阵**：所有验证程度都出现，确保证全景覆盖无遗漏；已证伪的条目只在覆盖矩阵的"不可利用"行出现，不在漏洞主体区重复

## 7. 降级规则

出现以下任一情况，ATK-CAND 必须降级为"高风险线索"（C3）或更低：

| 降级触发条件 | 降级目标 | 说明 |
|-------------|---------|------|
| 前置条件不完全满足 | C3 风险线索 | 部分条件不满足，无法完成攻击路径 |
| 攻击命令被安全机制阻断（AppArmor/Seccomp/网络策略） | C2 条件实证（已阻断） | 前置条件满足但攻击被阻断，标注阻断机制名称 |
| 差分证明不充分 | C2 条件实证 | 无法区分攻击效果与正常行为 |
| 影响不可观测 | C2 条件实证 | 攻击成功但副作用无法观测 |
| 未经审批执行高影响攻击 | C3 风险线索或更低 | 缺少审批门控，证据链不完整 |

### 降级路径

```
C1 实证复现 ──┬── 前置条件不完全满足 ──────→ C3 风险线索
              ├── 攻击被安全机制阻断 ──────→ C2 条件实证（已阻断）
              ├── 差分证明不充分 ──────────→ C2 条件实证
              ├── 影响不可观测 ────────────→ C2 条件实证
              └── 前置条件完全不满足 ──────→ ➖ 已证伪

C2 条件实证 ──┬── 发现新阻断证据 ──────────→ 维持 C2（更新阻断机制）
              └── 发现前置条件不完全满足 ──→ 降级为 C3 风险线索

C3 风险线索 ──┬── 补充验证后前置条件满足 ──→ 升级为 C2 或 C1
              └── 前置条件证伪 ────────────→ ➖ 已证伪
```

每个 ATK-CAND 必须闭环（确认/降级/放弃），不得遗留未决状态。
