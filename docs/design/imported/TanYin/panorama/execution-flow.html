读图要点（文字解说）：

① 静态与动态分离——左边 SKILL 套件是「工具箱」，装一次用永远；中间 session 目录是「工地」，每次测试新建一个，测试的全部状态（测到哪、发现了什么、还剩什么没测）都在这里的文件里，不在 AI 的会话记忆里。会话断了随便断，文件在就能恢复。

② 总控不直接碰目标——图里没有任何箭头从总控直达目标系统。总控只做四件事：跑账本命令、派子代理、验收提交文件、语义推导。真正发请求的是子代理（加载 web-blackbox 引擎 SKILL 后按引擎指导干活）和 CLI 引擎。

③ 子代理只写 submissions/，不写账本——所有子代理的产出先落在自己的提交目录，总控验收后才由账本命令写入八表。单写者模式：并发写账本的踩踏问题从结构上不存在。

④ 对外请求有统一关卡——任何请求先过 deny-list 机械检查+取票限速，多子代理共享一个速率配额，不会把目标打挂。

5. 上下文三层策略：压缩容忍 + 受管重启 + 断电恢复

长测试必然撞上下文上限。宿主（walcode 等）会自动压缩会话——但压缩时机不可控、摘要有损。探隐的答案不是二选一，是三层策略共用同一恢复协议（从盘上重定向：读 state.md+账本摘要+常驻集重载）——「节奏和状态」本来就不在会话里，在盘上：

层触发性质
① 压缩容忍（基线，永远在线）宿主自动压缩（时机不可控）每轮开头重定向协议：checkpoint（state.md）+账本扫描（unconsumed-facts/pending-intents/matrix-gaps）重建事实基准——压缩后下一轮边界自动恢复节奏。P3 每轮开头本来就从盘上重建基准，压缩损失被轮边界截断；轮中间被压缩的进行中分析由 checkpoint 兜底
② 受管重启（优选）上下文超阈值（0.75）/每 N 轮——在宿主压缩触发之前干净轮末边界主动换会话（下方时序图）——压缩是有损兜底，重启是无损优选；阈值前移使平时几乎不依赖①
③ 断电恢复（事故）崩溃/断电/会话意外终止同一恢复协议，state.md 是锚点——断电恢复是受管重启的特例

为什么不能只靠宿主自动压缩：①时机不可控（可能轮中间触发，进行中状态丢失）②有损摘要（fact ID/差分判定细节可能被摘要掉或摘错，不可验证）③纪律稀释（会话消息级注入的指令被摘要稀释——所以常驻集必须系统级注入）④注意力质量（在被压缩的长历史上推理，不如新会话+从盘上读精确状态）。三层策略把压缩降级为「可容忍的兜底」，无损恢复留给②。

5a. 受管重启时序：上下文满了怎么无损换会话

第②层的完整时序——每 N 轮或超阈值主动换会话：

[旧会话 · 第 12 轮末] 总控 检测上下文超阈值（或到达每 N 轮检查点） ↓ 总控 写 state.md：「round:12 / active:INT-g1-0021 / next:converge-check / threshold:0.75」 ↓ 总控 输出结束语（会话正常结束——不是崩溃，是存档换机） [新会话 · 立即] 自动档（宿主支持 headless 会话生成——自检探测，walcode run/serve 已实测可用）：总控 在旧会话内经执行通道 spawn walcode run "继续探隐 session G-g1"——无人值守，用户随时 walcode attach 观看 ↓ 兜底档（宿主无此能力）：总控输出精确恢复命令，用户 粘贴一次「继续探隐 session G-g1」——一次按键，不是流程中断 ↓ 总控 加载常驻集（SKILL.md：安全规则/铁律/循环骨架/命令索引——永远不卸载的部分） ↓ 总控 读 state.md + 账本摘要（ledger-intent-status / matrix-gaps——恢复的是「状态」不是「记忆」） ↓ 总控 从「next: converge-check」续上——第 13 轮开始，纪律强度与第 1 轮完全相同 [恢复后] session-viz 重新投影（projector 只读账本——视图反映恢复点状态） timeline 追加「managed-restart」事件（重启本身也留痕）

为什么这是设计核心而不是补丁：上下文溢出的实际表现不是干净失败，而是注意力衰减→纪律违反率上升→账本写错——恰好发生在最需要严谨的会话尾部。受管重启把「最虚弱的时刻」从会话尾部挪到会话开头（常驻集刚加载、纪律最完整的时刻）。状态在盘上所以重启无损；摘要纪律在所以新会话不被历史淹没——这就是 Context 支柱的运行时形态。

档位由自检决定，不由用户选：安装自检（B14）探测宿主 headless 会话生成能力——支持（如 walcode run/serve、claude -p）→默认自动档；不支持→兜底档（一次粘贴）。两档都无损：状态全在盘上，自动化是体验优化，不是正确性依赖。自动档护栏（防 spawn 失控）：①重启计入预算（budget.tsv 记 token 消耗）②重启速率上限（1 次/N 分钟——新会话若立即崩溃不会无限递归 spawn）③timeline 记 managed-restart 事件含 spawn 方式（auto/manual）④单活跃会话约束（同一 session 同时只有一个总控会话在跑）。

压缩容忍层在时序图里的位置：若宿主在旧会话第 12 轮中间就自动压缩了（未到 0.75 阈值）——第 12 轮剩余步骤靠 checkpoint 兜底完成，第 13 轮开头照常「读 state.md+账本扫描」重建基准，节奏自动恢复。①②③三层在运行时是叠加的：①永远在线兜住②的阈值前空窗，②在干净边界优选触发，③兜住一切意外——三者共用「从盘上重定向」，无需任何一层理解其他两层。
