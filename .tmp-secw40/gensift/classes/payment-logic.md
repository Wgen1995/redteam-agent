## ① 定义与危害
支付链路的正确性由不变式集合定义：回调幂等（INV-007）、退款不超原额（INV-008）、积分非负（INV-003）。违反形态=幂等键查重与状态更新非原子、退款校验只看单次不看累计、积分检查-扣减有并发窗口。危害=重复入账/重复发货、资金损失（退款超付）、积分双花。**本类无 sink 形态可锚：`pay()/refund()` 是全行业最普通的业务方法名，pattern 只会生产海量噪音——判据全部走 ⑥ 问句 + INV 条目，枚举分母不成立（pattern-undetectable，fixture 门豁免的依据）。**

## ② Source
支付回调/异步通知（webhook 端点、消息队列对账事件——**at-least-once 投递是常态，重复到达是设计内输入不是攻击**）、退款请求（含部分退款多次累计）、积分兑换/扣减请求（并发重放）、第三方重发的不同单号真实支付（阴性边界证据源）。

## ③ Sink 模式表指针
`patterns/payment-logic-java.pattern`（role: judgment-only，注释头声明，数据行可为空）。**无锚声明**：支付动词无法与正常业务调用区分，任何 ERE 锚的命中面 ≈ 全部支付代码。定位改由 source 侧（回调路由/消息监听器的 langpack source 枚举）+ INV 发卡（per invariant × module）驱动。

## ④ Propagator
回调载荷透传链：webhook→paymentService→ledgerService 的交易号/金额传播；金额换算（币种/汇率/分-元单位）是累计口径漂移的传播点（INV-008 的换算差通道）；幂等键若不在第一入口提取，中途任何分支都可能绕开查重。

## ⑤ 兜底机制（本类的"Sanitizer"——决策表三值）
```
幂等键唯一约束(交易号唯一索引,冲突即拒绝) × 回调状态更新 × 入口第一行提取 → 强
状态机护栏(仅 PENDING→PAID 单向迁移,非法迁移拒绝) × 状态更新 × 任意        → 强
对账批任务(T+1 差异修复)                                                  × 任意 → 上下文条件(只产 hint,禁 kills;事后修复不是事前防护)
内存级 Set 去重/先查后写两条语句/只依赖第三方不重发承诺                     × 任意 → 弱(等价无防护)
```
**多段兜底看全部**：有状态机≠有幂等（并发两个 PENDING→PAID 都合法）；对账兜底挂 requires_config（批任务停摆即失效）。

## ⑥ 判定流程（编号条目，含竞态问句与不变式引用）
C1 支付回调是否有幂等键查重且查重与状态更新原子（INV-007）？｜期望引用:回调入口的幂等键提取行 + 查重与更新所在事务边界｜推翻反例:交易号唯一索引冲突即整体拒绝（DDL 可引）｜反向:先查后写两条语句、内存去重、或依赖"第三方不重发"的注释承诺
C2 竞态问句：同一交易号的回调并发到达时，检查-提交间窗口是否被唯一约束/状态机单向迁移兜底（INV-007）？｜期望引用:并发重放路径上的约束定义与迁移守卫行｜推翻反例:PENDING→PAID 迁移带条件更新（affected rows=0 即拒绝）｜反向:读状态-判分支-写状态三段分离，双并发均读到 PENDING
C3 退款校验是否对累计口径原子生效（INV-008）？｜期望引用:累计退款 SUM 与本次金额的比较所在事务/锁范围｜推翻反例:条件更新 `paid - refunded >= ?` 原子成立｜反向:仅校验单次 refund ≤ 剩余额的内存读值，两次并发部分退款双过
C4 积分扣减是否保非负且原子（INV-003）？｜期望引用:扣减语句的余额下限条件（`balance >= ?` 条件更新）｜推翻反例:DB CHECK 约束 balance>=0 且冲突回滚｜反向:读余额-判断-减写三段分离（并发兑换双花）
C5 币种/单位换算是否单点且方向一致（INV-008 阴性边界的换算差通道）？｜期望引用:换算调用点唯一性与舍入规则声明行｜推翻反例:全链路单一 Money 值对象｜反向:各服务自行乘汇率且舍入口径不一
C6 资金状态变更是否留审计且可对账（INV-006 同族）？｜期望引用:入账/退款路径的审计写入行与对账字段｜推翻反例:审计同事务写入｜反向:审计异步可丢、对账字段缺失

## ⑦ 常见误报（FP 卡，只增+deprecate 留痕）
FP-1 重试产生的重复回调日志——记录重复≠状态重复（C1 查重通过的日志噪音）。
FP-2 第三方按不同单号重发的真实新支付——单号不同即新交易（INV-007 阴性边界）。
FP-3 对账批任务的重复修复动作——修复目标是幂等收敛，不是重复入账。
FP-4 争议裁决/客服补偿通道的额外打款——独立科目与审计（INV-008 阴性边界）。

## ⑧ 常见漏报与绕过（bypass 提示单——去尝试，不是去阅读）
B1 并发双回调：同一交易号两个并发 POST，先查后写窗口内均通过（出处：CWE-362 经典 TOCTOU，支付网关重试风暴实测形态）。
B2 幂等键取自载荷可变字段（商户侧订单号 vs 渠道交易号不一致）——键选择错位即查重失效。
B3 部分退款多次累计超付：单次校验通过、累计爆限。
B4 退款币种与支付币种不一致，汇率口径漂移吃掉上限。
B5 积分并发兑换：读-判-写三段分离，余额扣成负数。
B6 消息队列 at-least-once 重复消费回调事件——消费者无幂等键。
B7 回调验签通过但金额字段未与本地订单核对（改金额重放签名内字段）。

## ⑨ 利用前提与定级阶梯
见页首。High 验收：同一交易号两次提交得到两次成功状态变更（或累计退款超出原支付额的服务端落账），无需长篇推测。Medium 档需"对账可拦截"的批任务配置证据。
降级反例（B-109——出现下列形态时不应保持 high/critical，降级须引文）: 金额字段仅对账回显、结算以服务端价格源重算（引文）→ 不应保持 high

## ⑩ 根因修复
幂等键第一入口提取 + 唯一约束兜底；状态机单向迁移条件更新；退款/积分用条件更新（`WHERE paid - refunded >= ?` / `WHERE balance >= ?`）取代读-判-写；Money 值对象统一换算与舍入；审计与资金变更同事务。

## ⑪ 跨边界提示
Egress：支付服务向账本服务透传"已扣减"结果，账本侧不重验幂等——跨服务窗口；Ingress：消息队列对账事件 at-least-once 重复投递（INV-007 的消息侧变体）；第三方回调与内部事件双通道并发到达同一状态机。
