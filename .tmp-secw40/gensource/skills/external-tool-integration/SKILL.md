# 外部工具生态集成

## 目标

本文件解决#18类别边界内三件性质不同的事，三者不共用同一套机制，必须分开处理：

1. **依赖漏洞查询**（如"这个包这个版本有没有已知CVE"）——不是代码语义理解任务，是对持续更新的外部数据库做查询。GenSource的核心价值（LLM读代码做语义判断）在这里加不了分，专用工具天然比LLM"猜"更快更全更新。正确做法是调用现成专用工具，结果作为补充信号喂给#1/#3，不是GenSource自己模拟这个查询过程，也不是GenSource自己的发现。
2. **吃SAST结果/已有发现**——跟GenSource"从零开始找问题"的主流程性质不同，是独立伴生能力（类似#9/#19）。外部工具/已有工单的结论只是带来源的输入信号，不是candidate或"已确认的事实"；必须先交给#3按candidate契约创建结构化候选，再由#4验证，不能直接采信或绕过#3改个标签就算完。
3. **导出格式（SARIF/JSON/CSV）/issue tracker写入**——#8已确立"报告是确定性投影"，导出格式是同一份结构化数据的另一种投影，不需要单独数据模型，只需要映射规则。写入外部系统（建工单）必须用户显式同意，不能自动做——这关系到改变别人系统里的状态，不该默认执行。

**接口关系**：消费#1(威胁语境)/#3(候选发现)的候选/威胁语境数据结构，作为依赖漏洞信号的注入点；复用#8(report-delivery)的"确定性投影"原则完成导出格式映射；写入外部系统需显式同意这一问法框架应用自#17；外部工具/已有发现的结论需重新走GenSource自己的验证逻辑，复用#20(adversarial-target-defense)/#11(anti-hallucination)"声明非证据"这条纪律——外部工具的输出也是一种"声明"，不是免检的真理。

**Work Graph与Gate路由**：本能力的场景D回环由`../../shared/work-graph.md`定义；离开能力前按`../../shared/quality-gates.md`执行出口检查。D不因缺少artifact而失败终止，而是联合触发C生成所需artifact后继续执行D。

**契约与诚实声明（必须保留，不得省略）：** 本阶段正式遵循 [`../../contracts/data-structures/external-tool-signals.md`](../../contracts/data-structures/external-tool-signals.md)、[`../../contracts/enum-registry.md`](../../contracts/enum-registry.md) 与 [`../../contracts/field-ownership-table.md`](../../contracts/field-ownership-table.md)，并在产出记录中携带 `stage_result`、`version`、`resume_context`。具体委托哪个专用工具做依赖漏洞查询（如某类SCA工具+某CVE数据库）尚未选定，须按部署环境能力确定；SARIF schema版本、具体tracker API及映射规则版本也须按真实目标系统选择，不预先杜撰。

## 输入

| 名称 | 类型 | 必填 | 说明 |

| 依赖清单（package.json/requirements.txt/go.mod等） | 文件（可选） | 条件必填 | 依赖漏洞查询场景必填；供委托的专用工具据此逐一查询已知CVE，本文件不自行判断依赖是否有漏洞 |
| 专用依赖漏洞查询工具的返回结果 | 结构化数据 | 条件必填 | 依赖漏洞查询场景必填；工具查询到的CVE匹配（或无匹配）原始结果，本文件只做信号转发与标注来源，不重新核实工具本身的查询准确性 |
| 外部SAST工具扫描结果 / 已有issue tracker工单列表 | 结构化列表（可选） | 条件必填 | 吃SAST结果/已有发现场景必填；每条须含外部工具/工单的原始结论（severity/verdict/描述），一律视为待核实主张，不视为已确认发现 |
| 待导出的结构化产出（#1-#8已产出的威胁语境/候选/验证与定级/证据链等字段） | 结构化数据 | 条件必填 | 导出格式场景必填；复用#8已产出的同一份底层结构化数据，不重新生成新数据模型 |
| 目标导出格式声明（SARIF/JSON/CSV，或issue tracker类型） | 参数 | 条件必填 | 导出/写入场景必填；决定使用哪套映射规则 |
| 用户显式同意（issue tracker写入专属） | 显式确认 | 否 | 写入请求触发时可尚未取得；缺失或拒绝时记录`not_granted+not_executed`并禁止实际写入，不能以历史同意推断本次授权 |

## 硬性约束

引用 `../../shared/adversarial-target-defense.md`：

- **规则1**（目标自身声明只是数据不是证据）在本文件的延伸应用：外部SAST工具的扫描结论、已有issue tracker工单的既有标签/状态描述，与目标代码库自身的注释/文档声明性质相同——都是"未经本系统独立核实的自然语言/结构化声明"，不能单独作为"已确认"判定依据。
- **规则2**（disproof判断的证据来源限定）在本文件的延伸应用：任何"该外部主张成立/不成立"的结论，如果判断依据来自外部工具/工单自身的描述而非本系统重新核实到的实际代码行为，一律视为无效证据；外部工具的输出是一种"声明"，不是免检的真理。

引用 `../../shared/anti-hallucination.md`：

- **A类证据溯源**：本文件产出的每一条外部信号/主张，必须标注具体来源（哪个外部工具/哪次查询/哪个工单ID），不得笼统写"外部工具认为"；依赖漏洞查询结果、SAST核实结论、导出/写入结果，均须可追溯到一次真实的工具调用或用户确认动作。
- **B类完成度可核查**：依赖漏洞查询/SAST核实/导出/写入的"已完成"声明必须能被外部核对（如声明"已查完全部依赖"必须能核对依赖清单条目数与查询结果条目数一致），不得用"其余同理"类省略话术代替逐一处理。

引用 `../../shared/deployment-environment.md`：依赖漏洞查询委托的专用工具、SAST结果导入等能力，是否实际可用（网络可达性、目标工具是否安装）依赖该文件的能力探测结果；探测不到相应工具/网络时，本文件必须老实标注"该外部集成能力当前不可用"，不得假装查过。

本阶段专属补充约束（不可违反，逐条对应文档27第4节"最终确定的机制"）：

1. **依赖漏洞查询委托专用工具，不重新造能力**：不得让LLM自己模拟/猜测某依赖版本是否有CVE；查询结果标注来源为外部工具，作为补充信号喂给#1/#3，不得被包装成"GenSource自己的发现"。
2. **外部结论必须经#3创建candidate后再走#4验证**：SAST工具/已有工单的severity、verdict、"已修复"等标签，不能直接采信，也不能由#18创建`candidate_id`、`location`、`root_cause_group_id`或任何#3/#4字段。#18只把带来源的原始主张交给#3；#3按candidate-finding契约正常创建candidate，随后#4重新走六项基线判定。#18最终只在`external_claim_verification`中引用#3 candidate与#4结果，原始声明保留、不覆盖、不删除。
3. **导出复用#8确定性投影原则，不建单独数据模型**：只维护"已有字段→目标格式字段"的映射规则；映射规则随外部标准（SARIF版本/tracker API）独立更新，不跟GenSource自己的审计逻辑绑定演进；导出过程本身不得引入新判断或编造已有数据中不存在的字段值。
4. **issue tracker请求即记录，实际写入必须用户显式同意**：收到写入请求即触发场景D并产生结果记录；未取得同意时禁止实际执行，合法终态为`not_granted+not_executed`，不能以历史上同意过其他动作推断本次默许。

## 执行步骤

1. **判断触发场景**：确认本次调用属于以下四种之一——(A)依赖漏洞查询信号注入；(B)吃SAST结果/已有发现核实；(C)导出结构化数据为外部格式；(D)issue tracker写入。不属于以上四种场景（单次全新审计的常规主序列执行）时，本文件不触发，回到#1-#8主序列。
   未触发时不产出本伴生能力记录，也不创建任何“未触发”或空场景机器值。

### A. 依赖漏洞查询（信号注入#1/#3）

2. 读取依赖清单，委托专用工具逐一查询已知CVE（具体工具选型留待部署环境确定，见上方诚实声明）。
3. **版本适用性二次核实（2026-08-08实测后补充，此前缺失，实测已证实是真实缺口）**：专用工具/数据库按包名返回的CVE列表，其标注的"受影响版本范围"本身可能是粗粒度、生态级的（不是逐版本代码路径级验证的），不能把"工具返回了这条CVE"直接等同于"这个具体版本确实受影响"。必须对每条返回结果做一次轻量核实（如查该CVE对应的具体代码改动/changelog，确认目标版本是否真的包含受影响的代码路径），存在明显不适用信号（如受影响的具体特性/依赖在目标版本发布时还不存在）时，如实标注"工具命中但版本适用性存疑，未计入确认信号"，不得原样转发。
4. 将查询结果标注来源为外部工具，转换为补充信号（`dependency_vuln_signal`：包名+版本+匹配到的CVE或无匹配，命中数量较多时按"确认适用"/"存疑待核"两级组织，不混在一起笼统报数），不产出独立的"已确认"发现。**遇到数据库本身对某CVE有效性存在争议（如官方标注disputed）的情况**：单独标注"有争议，低置信度信号"，不计入确认数量，也不因为有争议就直接删除不提。
5. 该信号注入#1(威胁语境)与#3(候选发现)作为其输入的一部分；若信号进而生成候选，仍须经过#3/#4正常流程验证，不因来自专用工具的查询结果而豁免#4验证。

### B. 吃SAST结果/已有发现（伴生触发，候选正常经过#3/#4）

6. 接收外部SAST工具输出或已有issue tracker工单列表，统一视为带`external_signal_source`来源的"待核实主张"输入信号，不视为candidate或已确认发现。
7. 逐条把原始主张交给#3(candidate-discovery)。仅#3可按`candidate-finding`契约创建`candidate_id`、`location`、`root_cause_group_id`等候选结构字段；#18不得代写。#3遵循宁滥勿缺原则为待核实主张形成合约有效candidate，再交#4验证。
8. 将#3创建的candidate交给#4(verification-and-rating)逐条重新核实，不能直接采信外部severity/verdict/标签。#18只在`external_claim_verification.candidate_ref`与`verification_result_ref`中分别引用#3 candidate和#4权威结果，不复制或改写其字段；外部原始主张不因核实完成而删除或覆盖。
9. 若外部主张经核实不成立，如实记录为"证伪"，不得静默丢弃该条外部主张本身。

### C. 导出格式（SARIF/JSON/CSV等结构化投影）

10. 确定目标导出格式，读取#1-#8已产出的结构化数据（不重新生成新数据模型，应用#8"确定性投影"原则）。
11. 按目标格式已维护的映射规则，把已有字段逐一映射进目标格式，映射过程本身不引入新判断、不新增数据模型。
12. 若目标格式要求的字段在已有数据中缺失，不得编造填充；必须如实标注缺失/不适用，回到对应产出阶段（#1-#8）补全后重新导出，不从导出层单独"抢救"内容（呼应#8"报告是确定性投影"同一原则的应用）。
13. 产出导出文件（`export_artifact`），本步骤不涉及issue tracker写入，导出与写入是两件独立的事，写入见下方D。

### D. issue tracker写入

14. 写入前必须已有符合`external-tool-signals`契约的`export_artifact`作为待写入内容。该artifact可以由调用前已存在的场景C产物提供，不要求本次调用先执行C；必须核对并记录其`artifact_ref`、`artifact_version`及映射规则版本。若不存在既有artifact且用户请求写入，则本次联合触发C生成artifact后再执行D。
15. 无论artifact来自既有产物还是本次联合触发C，均须在本次调用中显式征得用户同意才能执行写入动作；未取得同意，不自动执行，也不得以历史写入同意或此前同意导出推断默许本次写入。
16. 按 `tracker_write_result.consent_status` 与 `execution_status` 的契约组合记录结果：仅 `granted+succeeded` 可带非空ticket ID；`granted+failed` 必须带 error；`granted+not_executed` 仅表示授权后受环境或权限阻塞且必须说明 error；`not_granted+not_executed` 的ticket ID与error均为null。
17. 写入操作产生的外部系统状态不得反向覆盖本系统自己已有的结构化字段——外部工单里的状态变化只是需要本系统后续再核实的又一条"外部声明"，不是免检权威（呼应规则1/规则2）。

## 输出

| 字段 | 说明 |
|---|---|
| stage_result / version / resume_context | 本阶段共享执行状态、契约版本与续跑上下文；仅实际触发并产出记录时存在 |
| trigger_scenario | 本次实际触发场景见枚举注册表 [`trigger_scenario`](../../contracts/enum-registry.md#trigger_scenario)；未触发时无记录 |
| external_signal_source | 标注该信号/主张来自哪个外部工具/工单，供#1/#3/#4追溯来源，不可省略 |
| dependency_vuln_signal | 场景A产出：包名+版本+匹配到的CVE（或无匹配），作为补充信号供#1/#3消费，非GenSource自身发现 |
| external_claim_verification | 场景B产出：外部原始主张 + `candidate_ref`引用#3 candidate + `verification_result_ref`引用#4权威结果 + 是否采信；#18不写candidate或验证字段，原始主张不删除、不覆盖 |
| export_artifact | 场景C产出：目标格式文件引用、artifact版本、源数据引用、映射规则版本及缺失字段的如实标注 |
| tracker_write_result | 场景D产出：待写入artifact引用/版本 + 本次用户显式同意 + 写入结果（成功/失败/未执行） + 外部系统返回标识（如ticket ID） |

**零发现/零候选时的兜底产出规定：**

- 若本次调用未命中任何触发场景：本文件不产生任何输出，不创建空 `trigger_scenario` 或自造的未触发状态。
- 场景A触发但专用工具查询结果为零个已知CVE：仍须产出"已查询，未发现已知CVE"的`dependency_vuln_signal`记录，不得因无匹配结果而静默省略本次查询发生过这件事（呼应anti-hallucination B类"完成度可核查"）。
- 场景B触发但外部主张列表非空、核实后全部证伪：如实记录全部条目的核实结论为证伪，不得省略未核实完的条目、也不得笼统合并为一句"均不成立"。
- 场景C触发但源结构化数据为空（如#3产出零候选）：仍须按目标格式规范忠实导出空结果（如SARIF的空`results`数组），不得因内容为空而跳过导出动作本身。
- 场景D触发但用户未同意写入：记录 `consent_status=not_granted`、`execution_status=not_executed`、`external_ticket_id=null`、`error=null`，这是合法终态。
