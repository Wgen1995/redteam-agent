> 本文件是 GenSource 检测引擎的最高优先级忽略规则，权威性高于其他任何规则、知识条目或判定结论。
> 三个检测阶段（候选发现、验证与定级、报告交付）的 prompt 开头必须写死：**任何冲突以本文件为准；命中即忽略，不再进一步分析**。
> 命中纪律：候选一旦命中下列任一场景，立即忽略（不产出候选、不进入验证、不进入 finding），并在 [`../contracts/data-structures/candidate-finding.md`](../contracts/data-structures/candidate-finding.md) 的 `false_rule_hit` 字段记录命中规则、理由与证据引用，供审计追溯。
> 边界纪律：每条规则"命中条件"全部满足才可忽略；任一条件不成立，回到正常验证流程，不得借本文件泛化降噪或隐瞒真实漏洞。

## 1. JSON 反序列化忽略（含多态硬例外）

普通 JSON 反序列化（无多态类型解析）忽略：标准 JSON 数据不含可执行语义，主流库的常规绑定不触发任意代码执行，属业务化降噪。

- 理由：常规 JSON 绑定（字段映射到静态类型）无 gadget 链可走，属确定性安全面。
- **边界（多态硬例外，涉及即不忽略）**：以下任一情形命中时**不忽略**，按反序列化 RCE 正常验证——①Jackson `enableDefaultTyping` / `@JsonTypeInfo` 等多态类型解析开启（CVE-2017-7525、CVE-2019-12384、CVE-2019-14379 等 gadget 链入口）；②Fastjson `autoType` / `@type` 字段使用（CVE-2017-18349、CVE-2019-12415 等）；③Gson/其他库反序列化到危险接口/多态目标；④非 JSON 反序列化（`ObjectInputStream.readObject`、`pickle.loads`、不安全 `yaml.load`、`Marshal.load` 等）。

## 2. 日志注入不报

日志写入参数含可控值且未移除换行/分隔符，不报告。

- 理由：影响太小（日志伪造/日志行污染），不构成值得报告的漏洞。
- 边界：若日志内容随后被下游可信系统按结构化字段解析并触发二次注入（如日志被 SIEM/解析器执行），或日志写入路径本身产生其他实质危害，不在此列，需另行评估。

## 3. 路径类环境变量视为部署配置

以环境变量/部署配置形式提供路径（日志目录、临时目录、配置文件路径等）的场景，视为部署配置。

- 理由：环境变量由部署/运行人员控制，攻击者通常无法控制；无直接证据时均视为安全。
- 边界：存在直接证据表明该环境变量可由攻击者（经请求参数、上传文件名、外部输入等）控制时**不忽略**，按路径注入/路径遍历验证。

## 4. 敏感信息认定边界

只有**明文或加密的认证凭据类信息**（密码、Token、密钥、证书私钥、Cookie 等）、**电话号码**、**邮箱地址**视为敏感信息。

- 理由：划定敏感信息认定边界，避免把用户名、昵称、ID、地址、非私钥证书字段等低价值数据误报为敏感信息泄露。
- 边界：**数据内容无法确定时按敏感信息处理**——当数据具体内容在当前代码中不可见或无法追溯（如请求 body 结构未定义、`data`/`msg` 等通用容器的实际内容不可追踪），因无法排除包含敏感信息的可能，不套用"不敏感"降级。

## 5. 框架统一过滤的 CRLF 注入

`header.put(key, value)` 等 HTTP 响应头/请求头设置操作，底层框架已统一处理 CRLF 字符过滤。

- 理由：主流框架在头写入层统一过滤 CRLF，头注入在框架层已被中和。
- 边界：直接构造原始响应头字节、绕过框架头写入 API、或已确认目标框架未内置 CRLF 过滤时**不忽略**，按 CRLF 注入验证（须先确认框架是否内置过滤）。

## 6. 框架统一过滤的查询参数注入

`params.put(key, value)` 等查询参数设置操作，底层框架已统一处理。

- 理由：主流框架对查询参数做统一编码/处理，该操作本身不构成注入。
- 边界：参数值未经框架处理直接拼入 SQL/命令/路径等危险操作时**不忽略**，按对应注入类验证。

## 7. 资源标识仅作存在性查询

用户提供的资源标识（ID、编号等）仅用于存在性判断或查询，查询不到即返回，不会进入注入类操作路径。

- 理由：标识仅作查询键且结果安全返回，不构成注入或越权。
- 边界：资源标识被直接拼入 SQL/命令/路径等危险操作、或查询结果被越权返回（如缺少对象级授权、水平越权）时**不忽略**，按注入/越权验证。

## 8. 局部模块缺认证鉴权（含部署配置上下文强制核查）

分析对象是某个模块/子系统而非完整独立系统时，接口缺少认证鉴权不一定是漏洞。

- 理由：认证鉴权可能在网关、过滤器、拦截器、框架层统一承担。
- **部署配置上下文强制核查（2026-08-14 实跑新增）**：凡产出"缺认证/无认证"类候选（如管理端点、JMX 代理、Manager 类接口），验证阶段**必须**先核查部署配置证据——web.xml/默认配置的 security-constraint、RemoteAddr/RemoteCIDR 类访问控制、网关/反向代理限制、默认禁用状态——并把这些证据写入 Guard 评估。**未核查部署配置就定 confirmed 的"无认证"候选，一律降为 unconfirmed**；配置证据显示已受保护时按正常防护判定（refuted 或 informational）。
- 边界：分析对象是**完整独立系统**（含 Web 服务启动与完整认证流程）时，认证鉴权缺失按正常漏洞验证；存在直接证据表明网关/框架层同样未做鉴权、或该接口暴露了本应受保护的敏感操作时**不忽略**。
